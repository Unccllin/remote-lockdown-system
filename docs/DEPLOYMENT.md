# Production Deployment Guide

This guide walks you through deploying the Remote Lockdown System to a
production server using Docker Compose. The production stack consists of:

- **PostgreSQL 16** — persistent database
- **Admin server** — Express API + built dashboard (Node.js 20)
- **Caddy** — reverse proxy with automatic HTTPS via Let's Encrypt

For a quick local smoke test (SQLite, no Postgres/Caddy), see
[Quick test deployment](#quick-test-deployment) at the end of this guide.

---

## Prerequisites

Before you begin, ensure you have:

- A Linux server (Ubuntu 22.04+ or Debian 12+ recommended) with:
  - **Docker 24+** and the `docker compose` v2 plugin installed
  - At least 2 GB RAM and 20 GB disk
  - Root or sudo access
- A **domain name** pointing at the server (e.g. `lockdown.example.com`)
- A **DNS A record** pointing your domain to the server's public IP address
- Ports **80** and **443** open on the server's firewall (Caddy needs these
  for HTTP-01 challenge and serving HTTPS)

Verify Docker is installed:

```bash
docker --version
docker compose version
```

---

## Step 1: Generate secrets

The server requires several cryptographic secrets. Generate them with the
included helper script:

```bash
./scripts/generate-secrets.sh
```

This writes four secret files to `./secrets/` (`jwt_secret.txt`,
`agent_key_pepper.txt`, `field_encryption_key.txt`,
`location_field_key.txt`) and prints the equivalent env-var values.

> **Critical:** Back up the `secrets/` directory to offline storage. If
> `FIELD_ENCRYPTION_KEY` or `LOCATION_FIELD_KEY` is lost, all encrypted
> data in the database becomes permanently unreadable. See
> [docs/BACKUP.md](./BACKUP.md) for the full backup procedure.

You will also need an `AGENT_SHARED_KEY` (not generated by the script).
Generate it manually:

```bash
openssl rand -hex 32
```

---

## Step 2: Create `.env.prod` from `.env.prod.example`

Copy the example env file and fill in your values:

```bash
cp .env.prod.example .env.prod
nano .env.prod
```

Set at minimum:

| Variable | Value |
|---|---|
| `DOMAIN` | Your domain, e.g. `lockdown.example.com` |
| `POSTGRES_DB` | Database name (default `lockdown`) |
| `POSTGRES_USER` | Database user (default `lockdown`) |
| `POSTGRES_PASSWORD` | A strong password (generate with `openssl rand -hex 32`) |
| `JWT_SECRET` | From `secrets/jwt_secret.txt` |
| `AGENT_SHARED_KEY` | Generated in Step 1 |
| `AGENT_KEY_PEPPER` | From `secrets/agent_key_pepper.txt` |
| `FIELD_ENCRYPTION_KEY` | From `secrets/field_encryption_key.txt` |
| `LOCATION_FIELD_KEY` | From `secrets/location_field_key.txt` |
| `CORS_ORIGIN` | `https://lockdown.example.com` (must match `DOMAIN`) |

> **Never commit `.env.prod` to git.** It is already in `.gitignore`.

---

## Step 3: Validate configuration

Before starting the stack, validate all configuration files:

```bash
./scripts/validate-docker.sh --all
```

This checks:

- `docker-compose.prod.yml` syntax (via `docker compose config` or YAML parse)
- `.env.prod` contains all keys defined in `.env.prod.example`
- `Caddyfile` syntax (via `caddy validate` or structural check)
- `Dockerfile.server` syntax (via `hadolint` or structural check)

All checks must pass (exit code 0) before continuing. If any check fails,
fix the reported issue and re-run.

---

## Step 4: Start the stack

Build and start all services in detached mode:

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

The first build may take several minutes (it compiles the dashboard with
Vite and installs PyInstaller for agent binary generation).

Check that all services are running:

```bash
docker compose -f docker-compose.prod.yml ps
```

All three services (`postgres`, `server`, `caddy`) should show status
`Up`. The `server` service waits for `postgres` to be healthy before
starting, so it may take 10–20 seconds to come up.

---

## Step 5: Verify health

Once Caddy has obtained its TLS certificate (usually under a minute on
first run), verify the stack is reachable:

```bash
curl https://lockdown.example.com/health
# or
curl https://lockdown.example.com/api/health
```

You should receive a JSON response with `status: ok`. If the request
fails or times out, see [Troubleshooting](#troubleshooting).

> **First-run certificate provisioning:** Caddy obtains certificates from
> Let's Encrypt via the HTTP-01 challenge. The DNS A record **must** be
> correctly pointed at the server before starting the stack, otherwise
> certificate issuance will fail and Caddy will retry with backoff.

---

## Step 6: Create the admin account

Create your first admin user via the setup endpoint:

```bash
curl -X POST https://lockdown.example.com/api/setup/create-admin \
  -H "Content-Type: application/json" \
  -d '{
    "username": "admin",
    "password": "YOUR_STRONG_PASSWORD"
  }'
```

> **Do this immediately after first deploy.** The setup endpoint is only
> available while no admin account exists; once the first admin is
> created it is disabled.

---

## Step 7: Enroll the first device

1. Log in to the dashboard at `https://lockdown.example.com`.
2. Navigate to **Devices → Enroll New Device**.
3. Follow the on-screen instructions to download the agent installer for
   the target platform and enroll the device.
4. Confirm the device appears in the device list and reports a healthy
   check-in.

## Alternative backend: the serverless Worker

The Docker stack is one of two backends. `serverless/` is a Cloudflare Worker
implementation of the same wire contract (agent ingress, admin API, downloads, and
the PBL `/v1/*` CBOR routes), with all state in KV. See
[serverless/README.md](../serverless/README.md) for bindings, secrets, local
verification (`make verify-worker`) and the publish step.

## The generic (fleet) agent installer

A Worker cannot run `makensis`, so the serverless backend does not build an
installer per device. Instead it serves **one** installer for the whole fleet
from KV key `binary:installer` (`GET /api/download/installer`, the link on the
dashboard's enrolment page). Its configuration is claimed at install time from a
15-minute enrolment token.

```bash
# 1. Build the PyInstaller binaries (Windows; produces agent/dist/*.exe)
pwsh agent/build.ps1

# 2. Compile the NSIS wrapper (Linux or Windows host with makensis)
scripts/build-generic-installer.sh

# 3. Publish it — the dashboard link serves this key
cd serverless && npx wrangler kv key put --binding=LOCKDOWN_KV \
  binary:installer --path ../installer/generic/dist/lockdown-installer.exe
```

Install (interactive, or silent for scripted rollout):

```powershell
.\lockdown-installer.exe                                     # wizard
.\lockdown-installer.exe /S --token=<TOKEN> [--server-url=<URL>]
```

`--server-url` defaults to the backend the installer was built with, so a rollout
only needs to hand out a token.

The wrapper only packages: staging, the Add/Remove Programs entry and the
uninstaller. Enrolment, `config.json`, the lockdown folder, the scheduled-task
persistence, tamper protection and the check-in verification all run through
`lockdown-installer.exe` (`agent/installer.py`) — the same CLI installer a
per-device deployment uses — so there is one install path, not two.

**Removal is authorized by the backend.** The uninstaller asks for a token from
`POST /api/agent/uninstall-auth` (valid 5 minutes) and refuses to remove anything
without one; the agent's binary, config and state files carry DENY-DELETE ACLs,
so a local administrator cannot simply delete the install either. This is
intentional: an anti-theft agent with an unauthenticated uninstaller has shipped
the bypass it exists to prevent.

### Per-device installers use the same engine

The self-hosted dashboard can also build an installer for one already-created
device — the one-click `.exe` (`GET /api/installer/:id/nsis`, the button on the
enrolment page) and the ZIP (`GET /api/installer/:id`). Neither implements
installation itself any more: both stage `lockdown-agent.exe` plus
`lockdown-installer.exe` and run

```powershell
lockdown-installer.exe --config-file config.json --silent
```

i.e. the same `agent/installer.py` path a fleet install uses. That matters for
more than tidiness: the generated installers used to register `sc.exe` services
(NSIS) or NSSM services (ZIP), and the agent implements no SCM handshake, so
Windows failed the service with 1053 and terminated the process about 30 seconds
after every boot — a device that checked in once and then went dark. The ZIP
path additionally degraded to a non-persistent `Start-Process` whenever
`nssm.exe` was not already installed.

Both require `lockdown-installer.exe` next to the agent binary when generating
(the routes return 503 without it); build it with `agent/installer.spec`.


## Verify the stack locally before you deploy it

The API E2E suite (`tests/e2e/`) boots Express **in-process on SQLite** via
supertest — it never exercises the container, PostgreSQL 16, or the static
dashboard. So a green test run does not prove the deployment works.

`scripts/verify-docker-stack.sh` does prove it, on this machine:

```bash
./scripts/verify-docker-stack.sh          # build image, run postgres + server, smoke, tear down
./scripts/verify-docker-stack.sh --keep   # leave it running for manual poking
```

It builds the **production image** from `Dockerfile.server`, starts PostgreSQL 16
and the server with the production env wiring, waits for the DB-backed readiness
probe, then checks over HTTP:

- `GET /api/health` → 200, and `/api/health/ready` becomes ready (DB reachable,
  migrations applied);
- `GET /api/devices` without a token → **401** (auth enforced in the container);
- `GET /` → 200 `text/html` (the built dashboard is in the image and served
  same-origin);
- `POST /api/setup/create-admin` → token, then `/api/devices` with it → 200;
- `POST /api/devices` → agent key, then `POST /api/agent/checkin` with that key
  → the agent's own ingress works;
- a second `create-admin` → 403/409 (the first-admin takeover guard holds).

It runs under its own compose project (`pbl-verify`), publishes only to
`127.0.0.1`, and removes its volumes on exit, so it cannot collide with a real
deployment. `make verify-env` calls it through `scripts/validate-docker.sh
--live`.

### Port conflicts: Caddy needs 80 and 443 free

Caddy terminates TLS on 80/443. If anything else on the host already holds those
ports — a VPN such as Tailscale (`ss -ltnp | grep :443`), another reverse proxy,
or a web server — `docker compose up` aborts with
`failed to bind host port 0.0.0.0:443/tcp: address already in use` and **nothing
else starts**. Two ways out:

```bash
# 1. Free the port (example: stop Tailscale's 443 listener)
sudo tailscale serve reset        # or: sudo systemctl stop tailscaled

# 2. Or keep Caddy off the privileged ports with an override
cat > docker-compose.local.yml <<'YAML'
services:
  caddy:
    ports: ["8080:80", "8443:443"]
YAML
docker compose --env-file .env.prod -f docker-compose.prod.yml \
               -f docker-compose.local.yml up -d
```

The local verification script sidesteps this entirely by not starting Caddy: it
reaches the server on loopback, because a placeholder `DOMAIN` cannot obtain a
certificate anyway. Caddy is the one component that cannot be verified locally —
check it on the real host with a real domain.

## SSL / TLS: Caddy auto-HTTPS

Caddy automatically provisions and renews TLS certificates from
Let's Encrypt for the domain specified in `{$DOMAIN}` (read from
`.env.prod`). No manual certificate management is required.

Requirements for automatic HTTPS to work:

- Ports 80 and 443 must be reachable from the public internet (the
  HTTP-01 challenge uses port 80).
- The DNS A record for your domain must point at the server's public IP.
- The `DOMAIN` in `.env.prod` must match the domain clients will use.

Caddy stores certificate data in the `caddy_data` and `caddy_config`
Docker volumes, which persist across container restarts.

## Firewall recommendations

Restrict inbound traffic to only what the stack needs:

| Port | Protocol | Source | Purpose |
|---|---|---|---|
| 22 | TCP | your IP / VPN only | SSH administration |
| 80 | TCP | anywhere | HTTP → HTTPS redirect, Let's Encrypt HTTP-01 challenge |
| 443 | TCP | anywhere | HTTPS (dashboard + API) |

Block all other inbound ports. PostgreSQL (5432) and the server (3001)
must **not** be exposed publicly — they communicate over the internal
Docker network only.

Example with `ufw`:

```bash
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp from <your_admin_ip>
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
```

## Updating the system

To update to a new release:

### 1. Back up first

**Always take a backup before updating.** See
[docs/BACKUP.md](./BACKUP.md) for the full backup procedure. At minimum:

```bash
./scripts/backup.sh
```

This produces an encrypted archive containing the database dump, secrets,
and config files. Store it off-server before proceeding.

### 2. Pull the new code

```bash
git pull origin main
```

### 3. Run any database migrations

If the release includes schema migrations, run them before restarting:

```bash
docker compose -f docker-compose.prod.yml exec server node server/src/db/migrate.js
```

> Check the release notes for each version to see whether a migration is
> required.

### 4. Rebuild and restart

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Docker Compose recreates only the containers whose images or configs
changed. PostgreSQL data, Caddy certificates, and agent binaries persist
in their named volumes.

### 5. Verify

```bash
curl https://lockdown.example.com/api/health
docker compose -f docker-compose.prod.yml ps
```

### 6. Uninstall tokens issued before the D-221 upgrade expire on 2027-02-04

An uninstall token used to be `HMAC(ADMIN_TOKEN, 5-minute window)` — the **same string for every
device** in the deployment. Since D-221 it is bound to one device
(`HMAC_SHA256(ADMIN_TOKEN, "<device_id>:<window>")`).

A server upgraded past D-221 still accepts the old form, so an operator who is mid-change is not
stranded, but **that acceptance ends on 2027-02-04**. From then on a token derived the old way is
rejected:

| Question | Answer |
|---|---|
| Does an agent need updating for this? | **No.** A pre-D-221 agent already sends `device_id` and authenticates with its device key, and the server binds the token to the authenticated device row. Old agent + new server is issued and verified normally. |
| What actually stops working? | A **token** computed under the old scheme and presented after the date — one staged in a runbook, a script, a ticket, or a chat message before you upgraded. |
| What should I do? | Use uninstall tokens inside their 5-minute life instead of staging them. A token you fetched before upgrading should be used before 2027-02-04, or simply re-requested after it — the request path is unchanged. |

The date is not a comment to remember: `scripts/test_cross_surface_contract.py` fails on it with the
exact deletion checklist, and the Express and Worker suites fail on the same day. Both servers also
echo `deprecated_scheme_sunset` in the verification response when the old form is accepted, so a live
deployment reports its own state.

> **Limitation, stated because it affects any fleet-wide instruction:** this server does **not**
> record which agent version a device runs. `/api/agent/update` reads `x-agent-version` to decide
> whether an update is available and then discards it, and the `devices` table has no version
> column — so "is every agent on version X?" cannot be answered from the dashboard or the API.
> That gap is tracked as **D-222** in `docs/adr/PBL-DEBT-LEDGER.md`. It does not affect the sunset
> above, which needs no agent change at all.

## Troubleshooting

### Common issues

#### Caddy fails to obtain a certificate

- Verify the DNS A record points at the server: `dig lockdown.example.com +short`
- Verify ports 80 and 443 are open: `curl -v http://lockdown.example.com`
- Check Caddy logs: `docker compose -f docker-compose.prod.yml logs caddy`
- Let's Encrypt has rate limits — repeated failed attempts will trigger
  backoff. Use the staging CA for testing if needed (configure in
  `Caddyfile`).

#### Server won't start (missing env vars)

- Run `./scripts/validate-docker.sh --env` to confirm `.env.prod` is
  complete.
- Check server logs:
  `docker compose -f docker-compose.prod.yml logs server`
- The server refuses to start in production with missing or weak secrets
  (see `scripts/validate-env.sh`).

#### PostgreSQL connection errors

- Ensure the `postgres` container is healthy:
  `docker compose -f docker-compose.prod.yml ps postgres`
- Verify `POSTGRES_PASSWORD` in `.env.prod` matches what was set when the
  volume was first created. If you change it, you must remove the
  `postgres_data` volume and reinitialize (this destroys all data — back
  up first).

#### Health check returns 502 / connection refused

- The `server` container may still be starting. Wait 30 seconds and
  retry.
- Check that the server is listening on port 3001 inside the container:
  `docker compose -f docker-compose.prod.yml exec server wget -qO- http://localhost:3001/api/health`

### Viewing logs

```bash
# All services
docker compose -f docker-compose.prod.yml logs --tail=100

# A single service
docker compose -f docker-compose.prod.yml logs --tail=100 server

# Follow live logs
docker compose -f docker-compose.prod.yml logs -f
```

### Health checks

```bash
# Stack status
docker compose -f docker-compose.prod.yml ps

# Server health endpoint
curl -s https://lockdown.example.com/api/health | jq

# PostgreSQL readiness (inside the container)
docker compose -f docker-compose.prod.yml exec postgres pg_isready -U lockdown
```

### Full reset (destroys all data)

```bash
docker compose -f docker-compose.prod.yml down -v
```

> This removes all volumes including the database and Caddy certificates.
> Only use this for a fresh start in a non-production environment.

## Quick test deployment

For a quick local smoke test that uses SQLite instead of PostgreSQL and
skips Caddy entirely, use the test compose file:

```bash
# Build and start the server in SQLite mode
docker compose -f docker-compose.test.yml up -d --build

# Wait for it to be healthy
docker compose -f docker-compose.test.yml ps

# Hit the health endpoint
curl http://localhost:3001/api/health

# Create an admin (only available before any admin exists)
curl -X POST http://localhost:3001/api/setup/create-admin \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"TestPass123!"}'

# Clean up
docker compose -f docker-compose.test.yml down -v
```

The test stack uses placeholder secrets and a short retention window. It
is intended for validation only — **never expose it to the public
internet**.
