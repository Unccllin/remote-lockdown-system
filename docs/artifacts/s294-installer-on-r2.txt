--- [2] two things that made it look broken, and were not ---
a. `wrangler r2 object put` writes to the LOCAL simulator by default:
     "Resource location: local — Use --remote if you want to access the remote instance."
   The first upload landed nowhere that serves traffic. The R2 object only exists after --remote.

b. KV-first precedence shadows a new R2 object. `readBinary()` reads KV first (deliberately: an
   artifact that still fits stays where the existing tooling puts it), and KV still held the stale
   18,628,686-byte `binary:installer`. So the deploy was correct, the object was correct, and the
   endpoint kept serving the old bytes. Deleting the KV key migrated the key to R2:
     npx wrangler kv key delete --binding=LOCKDOWN_KV --remote "binary:installer"
   KV deletes propagate in under a minute — the endpoint kept answering the old body for ~45 s
   after the delete, then switched. Verified by cache-busted requests (?x=<rand>) so the edge cache
   was ruled out rather than assumed.

--- [4] the risk this exposed, for the release process ---
  /api/download/* answers with `Cache-Control: public, max-age=3600`. A republished artifact can
  therefore be served stale by any cache — browser or edge — for up to an hour, and the URL has no
  version component to bust it. It did not bite here (cache-busted and plain requests agreed once KV
  settled), but after any republish a user's plain download may be the previous build. Options:
  shorten max-age, key the URL on x-content-sha256, or serve with `no-cache` + ETag so a conditional
  request revalidates. Not changed in this session; recorded as the next thing to decide.
