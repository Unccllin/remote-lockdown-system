# S370 — D-230: the geolocation key is restricted and never a placeholder

Review finding S9 · ledger entry D-230 · decision taken by the owner: "restrict the key + stop serving
placeholders" (the server-side-lookup alternative was recorded as available but deferred)

## What the defect was

The deployment's `GOOGLE_API_KEY` was spread into nine response sites across two backends (4 in
`serverless/worker.ts`, 1 in the agent runtime settings, 3 in `server/src/routes/enroll.js` and
`devices.js`), so every device could read the key out of its own enrolment response — and the key in
place was the **placeholder** `ROT-TEST-…`, which cannot work at all. The agent then failed BSSID
resolution and silently fell back to city-level IP location with nothing in the log to say why.

## What changed

- **One rule per deployable.** `serverless/kv-store.ts` gained `servedGeolocationKey()` /
  `geolocationKeyField()`; the Express side has the same pair in `server/src/lib/geolocationKey.js`.
  Duplicated rather than shared because the two backends are separate artefacts with no common module —
  the same reason the HMAC verifier and the timing-safe comparison exist on both sides.
- **Placeholders are "no key".** `ROT-TEST-…`, `changeme`, `placeholder`, `your-key`, `example…`, `xxx…`
  are treated as unset: the field is omitted from responses and the agent's runtime settings report
  `null`, so it falls back knowingly instead of presenting a key that cannot work.
- **The boundary is deliberate and documented in both files**: the pattern does *not* match "test"
  anywhere, because test suites legitimately use synthetic keys like `test-google-key` — 22 fixtures do,
  and rewriting them would have turned a rule about a *deployed* placeholder into a rule about a word.
- **The deployment step is written down** (`docs/SERVERLESS-DEPLOY.md`): restrict the key in Google
  Cloud to the Geolocation API only, with a daily quota, because an unrestrained key is a billing
  incident waiting for the first extracted device.

## Tests

## Residuals

- **A real key is still extractable by any device** — that is inherent to the design chosen (the agent
  resolves BSSIDs itself). Restriction and quota bound the damage; removing it entirely is the
  server-side-lookup option, which reworks the agent's offline resolve path and is deferred, not
  dismissed.
- **Nothing verifies the key's *scope*.** The Worker cannot ask Google whether a key is restricted; the
  rule here only catches placeholders. Restriction remains a deployment action, stated in the docs.
- **`GOOGLE_API_KEY` is still the placeholder in production**, so devices currently get honest IP-level
  location. Setting a real, restricted key is an owner action.
