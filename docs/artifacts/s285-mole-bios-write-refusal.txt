--- [4] the reading that explains it ---
  HP_BIOSPassword:  Setup Password     IsSet=1     <- a BIOS Setup password exists on this unit
                    Power-On Password  IsSet=0     <- no PBA password (PBA was off, as intended)
  agent config:     uefi_password      4 characters
  agent.log:        "Setup password was pre-existing - not clearing (admin manages it)"
  The agent never set this unit's Setup password (the log says so), yet it signs every
  SetBIOSSetting call with the 4-character value in its config. HP returns 4 ('Failed') for
  each critical write, the layer rolls back, and the ACK says boot_lock_status=partial.
  -> the UEFI layer cannot succeed on MOLE until the REAL BIOS Setup password is in the agent
     config (UEFI_PASSWORD) or is cleared in BIOS Setup. That is an operator secret, not a code bug.

--- [5] what was NOT done, and why ---
  No BIOS write was attempted to confirm the password hypothesis. The cheapest confirmation is a
  no-op write (SetBIOSSetting with the setting's current value), but a wrong password on HP firmware
  can raise the failed-attempt count, and this unit's boot state is already the fragile part of the
  lab. The conclusion above rests on IsSet=1 + "password was pre-existing" + return code 4, each
  measured, and is stated as the cause that fits all three rather than as a proven one.

--- [6] a smaller code question this raises ---
  apply_boot_lockdown already refuses when a Setup password exists and none is configured. It does
  not check whether the configured password is the RIGHT one, so it proceeds, fails three critical
  writes and rolls back. A pre-flight probe (one no-op write, reported honestly) would turn three
  red lines and a rollback into one clear sentence before any state is touched.
