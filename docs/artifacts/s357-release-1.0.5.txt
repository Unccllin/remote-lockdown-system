# S357 — release 1.0.5 built on MOLE, signed, published, and self-installed on a device

2026-11-26 · Windows build host: MOLE (`C:\Python314`, PyInstaller 6.22.3) · signing host:
the lab laptop (`~/.lockdown-secrets/update_signing.key`) · publish target: Cloudflare KV
namespace `LOCKDOWN_KV` 84b24c0c… (remote)

This release carries the certificate-addressed TPM seal key
(`docs/artifacts/s357-tpm-cert-seal.txt`). Everything below is a measured run, not a plan.

## 1. Why 1.0.5 and not 1.0.4

`AGENT_VERSION` was already `1.0.4`, and MOLE **was already running a 1.0.4 build**
(`build=20261119.32849efe4235`, installed 2026-11-19) that predates the TPM fix. Publishing
"1.0.4" would have left that machine reporting itself up to date with code it does not have —
the exact ambiguity `agent.py`'s version comment exists to prevent (S286/S310). So the
functional change bumps to **1.0.5** and the fleet converges upward.

## 2. Build — two scripts, and why the second one was needed

First pass used `scripts/build-windows-artifacts.ps1` (the CI script). The binaries were
valid (PE=True, correct sizes) but reported:

```
lockdown-agent 1.0.5 (frozen=True, build=unknown.unknown)
```

`agent.py` documents that the build id is stamped by `agent/build.ps1` immediately before
PyInstaller so two binaries cannot share an identity. A published release with
`build=unknown.unknown` is precisely the S286 defect. Rebuilt through `agent/build.ps1`:

```
Build identity: 20261126.69a3e4156d16
  OK   dist\lockdown-agent.exe (16.1 MB)
  OK   dist\lockdown-watchdog.exe (8.5 MB)
  OK   dist\lockdown-installer.exe (15.1 MB)
    lockdown-service.exe          9,494,908 bytes  PE=True      (build-windows-artifacts -Only service)

lockdown-agent 1.0.5 (frozen=True, build=20261126.69a3e4156d16)
```

No git on the build host, so the build id is `build.ps1`'s documented fallback: a SHA-256
over the agent sources.

```

  --artifact win=agent/staging/1.0.5/lockdown-agent.exe \
  --key ~/.lockdown-secrets/update_signing.key --out agent-release.json
```

The message is `v1:1.0.5:09a2d3e6…` and the signer is Python. Verified independently with

## 6. A production defect was found on the way: the mutation chain wedges permanently

While waiting for MOLE to pick the release up, check-ins were failing:

```
[WARNING] Check-in failed: … Read timed out. (read timeout=15)     (from 11:41 onward)
wrangler tail:  POST /api/agent/checkin - Canceled
```

Isolation probes from the laptop:

| request | result |
|---|---|
| `GET /api/health` | 200, 0.66 s |
| `GET /api/agent/update?platform=win` | 401, 0.72 s |
| `GET /api/devices` | 401, 0.60 s |
| `POST /api/setup/create-admin` (not serialised) | 409, 0.56 s |
| `POST /api/agent/checkin` (serialised) | **no response in 40 s** |
| `POST /api/agent/command-ack` (serialised) | **no response in 25 s** |

`worker.ts:365` keeps a module-level `mutationChain`, and `serializeMutation` queues every
mutation behind the previous one with no timeout. Only the two serialised agent routes hung,
so one handler that never settled wedged the chain for that isolate — check-in **and**
command-ack, i.e. the device was effectively unreachable while reporting a healthy network.
An unserialised `POST` proved it was the chain and not the Worker as a whole.

Cleared by redeploying the same committed code (`wrangler deploy`, version `bf0b81f7`), which
recreates isolates; the unsigned check-in then answered 401 in 0.73 s. Filed as **D-225** —
the wedge itself is a design defect that a redeploy must not be the standard remedy for.

## 8. What this release still does not prove

- **Only one Windows device took it.** FRANKENSTEIN (1.0.0) is powered off, so the fleet is
  now split 1.0.5 / 1.0.0 rather than 1.0.4 / 1.0.0.
- **No Authenticode signature.** The binaries are unsigned executables; the update chain is
  authenticated by Ed25519 metadata over the SHA-256, which is a different property from
  Windows trusting the publisher (see D-130 for the firmware size of this, and
  `docs/CODE_SIGNING.md` for the product).
- **`binary:lockscreen` and `binary:installer` were not rebuilt.** Neither is produced by
  `build.ps1`/`build-windows-artifacts.ps1` defaults and neither is touched by this change;
  they remain at their previous build.
- **D-225 is open**: the wedge can recur, and a redeploy is a workaround, not a fix.
