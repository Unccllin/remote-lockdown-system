## Attempt 1 — backup OK, restore FAILED
```
POST /api/admin/backups   -> 201  backups/2026-11-24T14-31-06-809Z.rmlb
  40659 bytes, counts {devices 2, commands 8, locations 79, audit 29, admins 1}
GET  /api/admin/backups   -> 200  1 object
POST /api/admin/restore   -> 400  'restore failed: KV PUT failed: 429 Too Many Requests'
```

## Root cause
```
restoreBackup() called createCommand()/addLocationReport() per record, and each of those
rewrites an index key. Workers KV allows ONE WRITE PER SECOND to the same key, so restoring a
device with 79 reports issued 79 back-to-back writes to location_index:<device> and the whole
restore failed. The smallest real fleet (2 devices, 79 reports) was enough to trigger it.
```

## Fix
```
serverless/backup.ts
  commands: records in one pass -> command_index once, command_index:<device> once per device
  locations: records in one pass -> saveLocationIndex() once per device
  the per-device merge reads the raw key instead of listCommandIdsForDevice(), which persists
  on a miss and would have been the second write in the same second
serverless/serverless-backup.test.ts
  new regression test: 25 locations + 25 commands -> each index written EXACTLY once,
  and both lists still come back complete
```
