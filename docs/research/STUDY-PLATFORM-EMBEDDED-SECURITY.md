## One-paragraph technical overview

The book is the only Intel-engineer-written deep dive on the **Security and Management Engine** (the chipset coprocessor called "management engine" on Core platforms and "security engine" on Atom SoCs — the predecessor of what Intel now brands CSME). It describes the engine as a small self-contained computer: its own CPU (ARC on early parts), 256 KB–1 MB internal SRAM, a 4–32 MB "borrowed" DRAM region hidden from the host by the BIOS, DMA engines that can only address host physical memory, a hardware cryptography engine, a ROM boot loader that is the root of trust, security fuses, and a HECI (host-embedded communication interface) PCI channel to the host. Firmware on flash is not encrypted but is integrity-protected: a manifest containing SHA-256 digests of every module is signed with a 2048-bit RSA key whose public-key hash is hardcoded in ROM. Hardening includes privileged/nonprivileged task isolation enforced by hardware modes, proprietary 32-bit ICV integrity checks plus AES-128-CBC encryption on pages swapped to host DRAM, whitelisted DMA access, per-file AES-CTR + HMAC secure storage with fuse-derived keys, return-address scrambling, and stack DMZ pages. On top of that substrate the book documents the applications: **EPID** anonymous attestation with the SIGMA mutual-auth/session protocol, **Intel Boot Guard** measured/verified boot via an ACM + OEM key manifest + IBBM + Field Programmable Fuses, **Intel PTT** firmware TPM, **PAVP** protected A/V path, **DAL** (a signed-Java-applet loader), **IPT** (TOTP/OCRA tokens + Protected Transaction Display), and the engine's role in **Intel Anti-Theft** — the direct historical predecessor of this project, in which the engine enforces an *unconditional platform shutdown* when theft is detected. For PBL, the book matters in three ways: (1) it documents exactly which signals exist below the UEFI layer (fuses, HECI, end-of-POST semantics) that PBL's `AmtCheck.c`/`DciCheck.c` only approximate; (2) Intel AT is working prior art for a pre-boot lock + remote poison pill + rendezvous timer + passphrase/token recovery design; (3) its EPID/SIGMA/Boot Guard material shows how Intel binds attestation and anti-rollback to silicon fuses — the same problems PBL solves in software with TPM PCRs and CBOR/COSE policy.

## 10-20+ key technical facts/mechanisms

1. **The engine's root of trust is a ROM boot loader; flash firmware is signed but never encrypted.** The ROM holds a hardcoded SHA-256 hash of Intel's RSA-2048 public key; at boot it hashes the public key carried in the manifest, verifies the manifest signature (RSA-2048 + SHA-256 + PKCS#1), then verifies each module's SHA-256 digest. Modules may be Huffman- or LZMA-compressed; hashing is done on the *decompressed* image — a deliberate memory/size tradeoff the author flags as "arguably a poor security design practice" because unverified compressed bytes land in memory before verification. Hardware/firmware compatibility (e.g., series-5 chipset ↔ firmware 6.x) is enforced by different signing keys per product. (ch. 4, https://link.springer.com/chapter/10.1007/978-1-4302-6572-6_4; ch. 9)

2. **The ME firmware SVN (security version number) gates update/downgrade.** The manifest header carries a firmware security version; an update from A to B proceeds only if `svn(B) >= svn(A)` — a lower number aborts as a rollback attack. This is the same anti-rollback pattern PBL wants for its own policy/verdict versioning. (ch. 4)

3. **The engine borrows 4–32 MB of host DRAM and must distrust it.** Pages swapped to the reserved DRAM region get a proprietary 32-bit ICV computed by dedicated hardware from the page data plus a 256-byte secret key (generated once, stored as an encrypted blob on flash; regenerated on each detected attack). Data pages are additionally encrypted with AES-128-CBC keyed from per-part fuses, with a random IV per paging-out; code pages are integrity-protected only (they're public on flash anyway). An ICV mismatch is treated as an active attack → *instant ungraceful platform shutdown* and ICV-key erasure. This mechanism exists specifically because the 2009 "Ring -3 rootkit" attack (Tereshkin/Wojtczuk, Black Hat) paged attacker code into the unprotected reserved region on Bearlake. (ch. 4)

4. **Task isolation is enforced by hardware privileged/nonprivileged modes plus a "treat idle tasks as privileged" trick.** Each firmware module (kernel, AMT, anti-theft, PAVP, EPID, DAL…) owns its assets — memory, NV files, hardware devices, semaphores — for their lifetime; cross-task calls go through a kernel inter-task call that copies params in/out and lets the callee reject the caller. Access violation ⇒ task termination or full engine reset. Kernel API surface is deliberately minimal. (ch. 4)

5. **DMA to host memory is a whitelist-gated kernel privilege.** Only pre-approved applications (hardcoded in the DMA driver) may DMA, each with minimum necessary direction (read-only/write-only); a tiny reviewed kernel component decides legitimate ranges; the engine is forbidden from touching VT-d and SMM regions. The host side must translate virtual→physical before handing addresses over HECI. (ch. 3, ch. 4)

6. **HECI is a small, unencrypted, client-ID-addressed control channel.** Max message ~1–12 KB (product-dependent), PCI device with ring-0 host driver (MEI), circular buffer, interrupt-signaled; client IDs are hardcoded pairs between host software and firmware tasks; no transport security — applications must layer their own encryption/integrity. BIOS talks to the engine over HECI pre-boot; the engine uses the **end-of-POST HECI message** to distinguish pre-boot MEBX commands from OS-time commands and rejects config commands not permitted after POST. (ch. 2, ch. 3)

7. **MEBX (ME BIOS extension) is the pre-boot configuration trust anchor for AMT.** Admin password, AMT on/off, IP/network config are set in MEBX which requires physical presence; the engine deliberately treats the *whole BIOS as untrusted* — a compromised BIOS can at most DoS the engine (e.g., withhold DRAM-init-done → degraded mode), never extract secrets. Passwords flow MEBX→engine only, never the reverse. (ch. 2)

8. **Secure storage is per-part keyed.** The kernel's storage manager encrypts NV files (keys, credentials, AMT passwords) in a dedicated SPI-flash partition with AES-128/256-CTR, integrity via HMAC-SHA-1/256, optional anti-replay; keys derive from unique-per-part security fuses so blobs cloned to another machine fail integrity. Anti-replay uses either an RTC-well monotonic counter (lost on coin-battery removal — blobs must be re-creatable) or RPMC flash; field programmable fuses remove both dependencies. (ch. 3, ch. 6)

9. **The engine's secure timer measures only elapsed time — it has no trustworthy wall clock.** Apps needing calendar time (e.g., EPID cert validation) fetch a timestamped OCSP response over SIGMA, store a baseline in secure storage, and compute `now = baseline + timer`; the engine re-calibrates every ~30 days and accepts cached OCSP responses up to 24 h old. Directly analogous to PBL's deadman/heartbeat problem: no secure RTC ⇒ time must be anchored to a signed server response. (ch. 3, ch. 5)

10. **Field Programmable Fuses (FPFs) are the engine's irreversible config/state store.** ~1024 fuses in a 32×32 array, ~1/4 reserved for lock/repair/redundancy; five usage models: single-bit OTP (e.g., "end of manufacturing" — kills OEM config HECI commands), single-bit multi-time (n fuses, odd burn count = true — used for **Anti-Theft enrollment state** so reflashing firmware can't un-enroll a stolen machine), multi-bit OTP (OEM root key hash, boot policy), multi-bit multi-time, and incremental integer (firmware/manifest SVNs). The fuse manager is its own isolated task; other tasks reach it only via kernel inter-task calls. (ch. 6)

11. **Boot Guard: CPU-verified ACM + OEM fuse policy + two signed manifests.** The OEM burns the SHA-256 hash of its root RSA-2048 public key plus boot policy (measured-boot on/off, verified-boot on/off, action on ACM failure, action on IBB failure) into FPFs at end-of-manufacturing — once burned, *even a compromised OEM root key cannot be rotated*. The ACM (Intel-signed, SVN-versioned, CPU-verified) loads the Key Manifest (OEM-root-signed; carries IBBM pubkey hash + SVN) and the IBBM (IBBM-key-signed; carries IBB hash + SVN), verifies the IBB, and asks the engine to bump fuse SVNs. Verified boot needs no TPM; measured boot routes through TXT into TPM PCRs. (ch. 6)

12. **Boot Guard failure actions are graduated, and the *engine* executes the shutdown.** On IBB/ACM verification failure the fused policy selects: unrestricted (boot anyway), remediation (ungraceful shutdown after ~30 min — enough for a tech to reflash), diagnostics (~1 min for debug data), or zero-tolerance (immediate shutdown, "generally not recommended" because it's undebuggable). SVN revocation is limited: it only catches rollback *after* a platform has once run a newer manifest — an attacker who blocks updates entirely defeats it. (ch. 6)

13. **The book covers TXT only at the level of "ACM measures the IBB into a TPM PCR."** There is no SENTER/SINIT/LCP/PCR-17-23 detail in this book — that depth lives in the Intel TXT MLE Developer's Guide already digested in `STUDY-INTEL-PLATFORM-SECURITY.md` (facts 7–13 there). The book does note measured boot satisfies the Windows Certification Program's "measure all boot components after the CRTM" requirement, and that TXT marks the platform trusted/untrusted against known-good references with configurable fallback (abort boot vs. degraded operation). (ch. 6)

14. **EPID = per-part unique private key in fuses + shared group public key ⇒ anonymous but revocable attestation.** Each chipset part gets a unique EPID private key burned (544-bit compressed-and-encrypted form for EPID 1.1; decompresses to 1312 bits) at Intel manufacturing; a group public key maps to hundreds–to–tens-of-millions of private keys. Three revocation tiers: private-key RL (key leaked → member revoked), signature-based RL (misbehaving signer revoked via its own signatures — requires a non-revocation proof per SIG-RL entry, capped at 50 entries/group for performance), and group RL (whole group revoked → re-provision clean members into a new group). Optional "base name" makes a platform's signatures linkable to a verifier — privacy-degrading, so platforms are advised to reject it by default. Basic signing takes ~2 s on the engine; pre-generated "presignature" caching cuts it ~95%. (ch. 5)

15. **SIGMA adds verifier authentication + ECDH session keys on top of one-way EPID.** The EPID authority doubles as a PKI root CA issuing X.509 verifier certificates; the platform hardcodes the authority's ECDSA root key and validates the verifier's cert chain plus OCSP non-revocation proofs (the engine never talks to OCSP directly — the verifier proxies). Message flow: M1 platform→verifier {group ID, a·G, optional OCSP challenge}; M4 verifier→platform {b·G, SIG-RL, cert chain, OCSP response}; then EPID signature + session keys (encryption + integrity) both ways. Used to provision IPT tokens and to authenticate the platform for premium services. (ch. 5, ch. 10)

16. **Intel AT is the direct prior art for this project — hardware lockdown driven by a rendezvous timer and a "poison pill."** Per Intel's briefs: theft detection triggers = (a) excessive failed pre-boot-auth logins, (b) expiry of a hardware-based **rendezvous timer** when the laptop misses scheduled check-ins with the central server (works with no network — local timer, hardware-enforced), (c) a remote encrypted "poison pill" message delivered over IP LAN/Wi-Fi at next check-in, or (d) AT 3.0: an encrypted, authenticated **SMS over 3G** delivered via a hardware-to-hardware link between the 3G card and the chipset — works with OS down/reinstalled or machine powered but offline, and can also wake for S3 standby protection. Consequences: block boot ("brick") and/or **hide/delete the crypto material blob in chipset** that the FDE vendor split-keyed into the ME, so even correct PBA credentials can't decrypt. Recovery: pre-provisioned local passphrase, one-time IT recovery token, or remote reactivation message/SMS. Survives OS reinstall, new HDD, boot-order changes. The book adds the enforcement-side detail Intel marketing omits: AT is a normal nonprivileged ME *application* that must remain available even against a physically-present attacker (availability requirement inverted — shutdown *is* the service), it invokes the engine's unconditional power-down capability, and its enrollment state lives in a "single-bit multi-time" FPF so firmware rollback can't un-enroll it. AT went EOL January 2015. (ch. 2, ch. 4, ch. 5, ch. 6; Intel/Dell/UNH AT briefs; Tom's Hardware AT 3.0)

17. **PTT = firmware TPM 1.2/2.0 implemented as an isolated ME task, with a patented fuse-space trick for the EK.** Rather than burning a 2048-bit RSA EK into fuses, Intel burns a 128-bit PRNG key + 128-bit seed + 16-bit iteration count (272 bits total, US patent 20100329455) from which the TPM task regenerates each probable prime via ANSI X9.31 AES-mode PRNG at runtime. EK revocation via `TPM2_ChangeEPS` flips an FPF so the fused EK material is never reused; EK *certificates* need not live on-device — they can be served from an online database. TPM extended localities 32–255 let other ME tasks consume TPM objects through kernel-mediated inter-task calls invisible to the host. (ch. 7)

18. **DAL runs Intel-signed Java applets; the same RSA key signs applets and firmware — separated by a manifest flag.** Applets ship with a manifest identical in form to the firmware manifest (applet ID, DAL flag, version + SVN, RSA-2048 signature, pubkey, SHA-256 of applet); because the boot ROM would accept an applet image as firmware (same signing key), the DAL flag in the manifest prevents cross-loading in both directions. Per-applet SVN is tracked in ME secure storage for rollback rejection. DAL gives each applet persistent per-platform encryption+integrity keys (derived from a random base string + applet ID) so applets can safely keep big state on host disk. DMA is *not* offered to applets. IPT ships as a DAL applet on Ultrabooks, native firmware where DAL is absent. (ch. 9, ch. 10)

19. **IPT = engine-hosted TOTP/OCRA token + PTD secure PIN pad via PAVP.** Token provisioning rides a SIGMA session (server = verifier; session keys SK protect delivery of the OTP seed + time baseline; metadata lives in ME secure storage or host-disk-wrapped by DAL keys). PTD renders a PAVP-protected randomized PIN-pad sprite invisible to the host: server encrypts sprite with SEK, wraps SEK in the SIGMA session key, engine injects SEK into the GPU; the host "IPT proxy" forwards raw click coordinates and only the server can map them to digits. Embedded PKI feature stores user RSA private keys in the engine, never exposed in the clear. (ch. 10)

20. **AMT is just another nonprivileged ME app — but a special one with its own network stacks.** Unlike other ME apps (which proxy networking through host software), AMT has firmware wired+wireless stacks sharing the host NIC (OOB-with-shared-NIC model); it works host-off/crashed. Config surfaces: MEBX (pre-POST HECI), LMS/UNS tray (local WS-MAN over HECI), and remote WS-MAN (older EOI/SOAP dropped in favor of WS-Management). Provisioning modes per Intel's AMT guide (not detailed in the book): host-based setup → **Client Control Mode** (user consent required for KVM/redirection; optional signed-nonce scheme to detect rogue provisioning), remote/PKI or MEBX setup → **Admin Control Mode** (full KVM/IDE-R/SOL/power control). PSK remote config was removed in AMT 11; TLS mandatory from CSME 19. (ch. 2; Intel AMT Implementation and Reference Guide)

21. **Defense-in-depth reaction ladder.** Minor violations → logged/ignored; suspected bugs → engine self-reset, with N resets in M seconds → recovery mode; violations attributable to attack (ICV mismatch, unauthorized task access) → ungraceful global reset of engine + host. Return-address XOR scrambling and no-access stack DMZ pages blunt stack exploits inside the engine. (ch. 4, ch. 11)

22. **Debugging is itself fused and signed.** Debug port is fused off on production parts; special production-signed firmware can re-enable it only on the single part whose salted 128-bit unique ID (SHA-256(uid || 32-bit random) truncated) it hardcodes — and it wipes top secrets (e.g., EPID private key) before opening the port. Relevant because PBL's `DciCheck.c` tries to detect exactly this class of debug enablement (USB DCI) from the host side. (ch. 3)

## Glossary terms

- **Security and Management Engine ("the engine"):** Intel's isolated chipset coprocessor — "management engine" on Core platforms, "security engine" on Atom SoCs; ancestor of CSME. ROM-rooted, fuse-keyed, self-contained RTOS.
- **HECI / MEI:** Host-Embedded Communication Interface — PCI-based, small (~1–12 KB) unencrypted message channel; client-ID addressed; host driver = MEI.
- **End-of-POST:** HECI message from BIOS that marks the MEBX→OS trust boundary; engine applies different command policy before vs. after it.
- **MEBX:** Management Engine BIOS Extension — pre-boot, physically-present admin config for ME/AMT.
- **Manifest:** Signed (RSA-2048/SHA-256) table of firmware modules' SHA-256 digests, versions, compression types; root key hash hardcoded in ROM.
- **ICV:** Proprietary 32-bit Integrity Check Value for pages swapped to borrowed DRAM; keyed (256-byte secret) binary-polynomial algorithm, not a hash.
- **FPF:** Field Programmable Fuse — OTP bits inside the engine; used for OEM key hashes, boot policy, SVN counters, AT enrollment.
- **FPF usage models:** single-bit OTP; single-bit multi-time (parity of n burns); multi-bit OTP; multi-bit multi-time; incremental integer (SVN).
- **ACM:** Authenticated Code Module — Intel-signed, SVN-versioned code verified by CPU for Boot Guard/TXT.
- **IBB / IBBM / Key Manifest:** Initial Boot Block, its signed manifest (IBB hash + SVN), and the OEM-root-signed manifest binding the IBBM pubkey hash.
- **Boot Guard modes:** measured boot (→ TPM PCR via TXT), verified boot (signature chain, no TPM needed), or both; failure actions unrestricted/remediation/diagnostics/zero-tolerance.
- **EPID:** Enhanced Privacy ID — group-signature anonymous attestation; unique private key per part in fuses, shared group public key; Priv-RL/Sig-RL/Group-RL revocation.
- **SIGMA:** SIGn-and-MAc protocol — one-way-anonymous mutual auth + ECDH session keys, verifier proven via EPID-authority-rooted X.509 + OCSP proofs.
- **Base name:** Optional EPID input making a platform's signatures linkable to a verifier.
- **PTT:** Platform Trust Technology — the ME-resident firmware TPM.
- **PAVP:** Protected Audio Video Path — hardware-isolated media/graphics path; also used for IPT's PIN-pad sprite.
- **DAL:** Dynamic Application Loader — JVM in an ME task for Intel-signed Java applets; DAL-flag manifests prevent firmware/applet image swaps.
- **IPT:** Identity Protection Technology — embedded TOTP/OCRA token + Protected Transaction Display.
- **Intel AT / poison pill / rendezvous timer:** Anti-Theft Technology — hardware theft-mode triggers (login-failure count, missed server rendezvous, remote pill over IP/3G-SMS) enforcing boot-block and/or crypto-material erasure; EOL Jan 2015.
- **CCM / ACM (AMT):** Client vs. Admin Control Mode — host-based provisioning ⇒ CCM (consent-gated KVM); PKI/MEBX provisioning ⇒ ACM (full OOB control).
- **RPMC:** Replay-Protected Monotonic Counter in flash — alternative to RTC-well counters for storage anti-replay.

## Security implications

- **The threat model explicitly assumes reflashed SPI flash.** ME security does not rely on the BIOS flash lock; integrity is rooted in ROM + signature. PBL conversely *does* rely on SPI write-protection bits it reads via `SpiProtections.c` — a weaker assumption the book's model shows is insufficient for a silicon vendor. (ch. 2, ch. 4)
- **"Brickability" is a feature with a blast radius.** Both Boot Guard zero-tolerance and AT can render a machine unbootable; the book notes immediate shutdown "is generally not recommended" because it's undebuggable and generates support calls. PBL's BLOCK verdict inherits the same tension — DEGRADED mode exists precisely to avoid bricking on ambiguous signals. (ch. 4, ch. 6)
- **Same-key signing across domains needs explicit domain separation.** DAL shares the firmware signing key; only a manifest flag stops an applet image from being loaded as firmware (and vice versa). PBL signs policy and verdicts — the C4/C1 formats must never be mutually substitutable. (ch. 9)
- **Anti-rollback by SVN only works if updates can land.** The book admits: an attacker who blocks manifest updates entirely defeats SVN revocation. Same caveat applies to PBL policy-version monotonicity and to the deadman timer as the compensating control — miss-check-in ⇒ lock is exactly the AT rendezvous-timer answer to "attacker prevents updates/contact." (ch. 6; Intel AT briefs)
- **Timer-only trust is fragile without a time anchor.** The ME has a secure *elapsed-time* counter but no wall clock; it anchors to OCSP timestamps and recalibrates every 30 days. E-DEADMAN's "24 h no contact ⇒ lock" has identical clock-skew/RTC-reset exposure — noted risk in GRAPH-SPEC.yaml — and the book's baseline+timer pattern is the reference fix. (ch. 3, ch. 5)
- **Unconditional power-off by an embedded agent is a DoS weapon if subverted.** The book warns malware exploiting an ME flaw could repeatedly force shutdown — the platform becomes a brick by software attack. For PBL, a forged verdict or leaked policy-signing key is the equivalent abuse path (D-205/D-130). (ch. 4)
- **BIOS/UEFI is outside the engine's trust boundary — and PBL lives inside that boundary.** The engine treats all BIOS (including MEBX) as untrusted: worst case a bad BIOS DoS-es the engine. PBL is a UEFI application and therefore *is* inside the attacker's boundary — every check (variables, PCI config, TCG protocol) can be lied to by earlier DXE code, reinforcing that PBL signals are indicators, not roots (D-129). (ch. 2)

## PBL-specific relevance

- **Intel AT ≈ this whole project's ancestor.** Map the parts: AT's *rendezvous timer* ⇒ E-DEADMAN (`agent.check_deadman`, `agent/agent.py` l. 2890) + heartbeat window; AT's *poison pill over IP/SMS* ⇒ server verdict fetch `Verdict.c` + `POST /v1/verdict` (`serverless/pbl/routes/verdict.ts`) + agent `handle_lockdown` (l. 1697); AT's *boot-block brick* ⇒ `Decision.c` BLOCK + `LockScreen.c`; AT's *crypto-material deletion in chipset* ⇒ PBL's FVE/BitLocker-key-withholding approach (`Fve.c`, D-120); AT's *local passphrase + one-time recovery token* ⇒ `Override.c` challenge/response + `serverless/pbl/routes/override.ts`; AT's *custom lock screen* ⇒ `LockScreen.c`. The big architectural difference: AT ran below the OS in silicon and survived reimages/HDD swaps; PBL runs at UEFI-application level + OS agent and is correspondingly more evadable but also deployable on non-vPro hardware.
- **AT's enrollment fuse is the hardware answer to "can a thief unenroll the machine?"** Intel burned enrollment as a multi-burn FPF (odd count = enrolled) precisely so a firmware reflash can't clear it. PBL's equivalent durable state is TPM NV + ESP policy blob (per D-200 note: "all durable state is in TPM NV and the ESP policy blob") — attacker-writable unless sealed to PCRs; the C5 tracking design (`enroll_tracking_pcr`) already moves in the fuse-analogue direction. (ch. 6; agent tracking code)
- **`AmtCheck.c` (l. 41–66) vs. the real thing.** The book documents the actual detection surfaces: ME presence = HECI PCI device (what PBL probes at B0:D22:F0); provisioning = ME firmware state reachable only via HECI commands; config trust boundary = end-of-POST gating; AMT capability = CCM vs. ACM control mode. PBL's conservative `Provisioned=TRUE` on bare HECI presence conflates "ME exists" with "AMT provisioned in ACM" — the book + AMT guide show the right path is a HECI `IPS_HostBasedSetupService`/control-mode query, which is D-127's close criterion.
- **`DciCheck.c` and the debug-port fuse model.** The book shows Intel's debug model is fuse-gated (production parts have debug fused off; signed per-part debug firmware is the only override). USB DCI is the host-visible edge of that model; the book reinforces why a PMC-register guess (current code) may miss the real enable bit living in flash-descriptor/fuse state (D-122).
- **TXT/Boot Guard boundary matches PBL's documented blind spot.** The book's picture (ACM + fuses + engine-enforced shutdown) confirms STUDY-INTEL-PLATFORM-SECURITY.md's core caveat: none of this is observable from a UEFI app — PBL can read UEFI vars, PCI config, ACPI, TPM — hence D-129's "indicators, not roots" posture. New detail from the book: Boot Guard *failure policy* is OEM-fused, so even a Boot-Guard-enabled machine may be fused to "unrestricted" (boot anyway) — PBL cannot tell; the platform-state digest should treat Boot Guard as unknown, never assumed-on.
- **HECI is the missing driver.** Nearly every gap in PBL's Intel checks (real AMT provisioning, PTT-vs-dTPM discrimination, ME firmware SVN, AT-style state) funnels through one missing capability: a pre-boot HECI/MEI client. Book gives the wire-level facts needed to write one: PCI device B0:D22:F0 (PBL already probes it), circular-buffer messages ≤ ~12 KB, client-ID-paired request/response, unencrypted transport ⇒ PBL must treat replies as unauthenticated unless app-level signing exists. (ch. 2, ch. 3; `AmtCheck.c`, `TpmClient.c`)
- **Server-side attestation design echoes EPID/SIGMA.** PBL's attest endpoint (`serverless/pbl/routes/attest.ts`) is a non-anonymous version of the same problem: prove a genuine enrolled platform + establish a fresh, time-anchored response. Two borrowable mechanisms: (a) EPID-style *nonce + signed-quote* challenge (PBL does this with TPM PCR quote — see `TpmClient.c`); (b) SIGMA's *cached vs. real-time OCSP freshness* model — maps directly to verdict TTL and the "verdicts stolen from another device/session" checks already in `Verdict.c` ll. 126–132.
- **E-TRACK (covert tracking) precedent.** Intel AT 3.0 shipped exactly this: GPS "Locator Beacon" on select 3G modems + server check-ins, while AT 1.x/2.x relied on software agents (Absolute Computrace et al.). PBL's `handle_track` (agent.py l. 2237, silent geolocation) + `PblDeviceStatus: tracking` verdict mapping replicates the agent-side half; the book/briefs show why the silent mode matters (thief keeps using machine → keeps beaconing) and its risk (any covert tracking must be consent/policy-gated — D-211 closed with stealth install).
- **Secure-storage split maps to PBL state layout.** ME rule: secrets ≤ ~KB in fused/secure flash partition, bulk data encrypted-and-blobbed to host disk (DAL host-storage-protection keys). PBL equivalent: TPM NV for small durable state, ESP/policy blob for the rest, agent DPAPI+HMAC state files (`agent.py` l. 114) for OS-side secrets.
- **Boot Guard's graduated failure policy = PBL's verdict ladder.** unrestricted / remediation-timer / diagnostics / zero-tolerance correspond almost one-to-one to PASS / DEGRADED-with-window / (unimplemented diagnostics path) / BLOCK — useful vocabulary when writing policy docs (`PBL-C4-Policy-Blob.md`).

## Known limitations / unverified items

1. **TXT internals are NOT in this book** beyond "the ACM measures the IBB into a TPM PCR" and a high-level MLE/trusted-untrusted description. The task's premise of "TXT deep internals — SENTER/SINIT/LCP/PCR 17–23" in this book is **not borne out by the actual TOC/text**; that material is covered by the Intel MLE Dev Guide in `STUDY-INTEL-PLATFORM-SECURITY.md` instead. (ch. 6, verified against full chapter text)
2. **Intel AT internals are also light in the book.** The book treats AT as an ME application (availability-inversion, power-down trigger, FPF enrollment bit, EPID client) but does **not** describe rendezvous-server protocol, timer parameters, poison-pill wire format, or crypto-unlock internals — those facts here come from Intel/Dell product briefs and AT 3.0 press coverage, which are marketing-level, not engineering specs. Wire protocols and HECI opcodes for AT are undocumented publicly. (ch. 2/4/5/6; Intel/Dell/UNH briefs)
3. **AMT provisioning models (CCM/ACM, PKI remote config, host-based setup) are not in the book** — the book defers to the 2009 AMT book (*Active Platform Management Demystified*, Kumar/Goel/Saint-Hilaire, Intel Press) and the AMT Implementation and Reference Guide. CCM/ACM facts cited here are from Intel's online AMT guide, not the book. (ch. 2)
4. **No engine CPU/architecture specifics beyond "ARC on early parts."** The book deliberately omits the processor model, kernel identity (now known publicly as MINIX/ThreadX-derived in later research), and most register-level detail; figure-level diagrams were not extractable from the HTML text.
5. **2014-era state.** Everything predates CSME rebranding (ME 11+), the 2017 CVE-2017-5689 AMT auth bypass, Boot Guard bypass research (e.g., Ermolov's work already in the other study note), EPID 2.0 deployment, and SGX shipping. Book explicitly describes "the latest engine release for 2014" (Haswell-era).
6. **Page numbers not cited** — chapters were read as SpringerLink HTML; figure contents (flows, manifest layouts, SIGMA sequence) are described but not reproduced.
7. **EPID math not verified** — the book intentionally gives interfaces/sizes, not algorithms; Brickell & Li (IEEE TDSC 2012) is the cited primary source but was not fetched.

## Outstanding questions

1. Can a pre-boot HECI client in `PblApp` issue `MKHI`/`IPS_*` queries for AMT control mode + ME firmware SVN — and are those commands stable/documented enough to close D-127 without a full MEI stack?
2. Is there any host-visible register or TPM NV index reflecting Boot Guard's fused enforcement policy (unrestricted vs. remediation vs. zero-tolerance), so `PlatformState.c` could distinguish "Boot Guard on, teeth" from "Boot Guard on, advisory"?
3. Should PBL adopt the ME's baseline+elapsed-timer pattern for E-DEADMAN — i.e., store a server-signed timestamp (verdict `iat`) as baseline in TPM NV and measure elapsed via `gRT->GetTime` deltas — to resist RTC reset/clock-skew (GRAPH-SPEC risk note on E-DEADMAN)?
4. Would an EPID-class anonymous attestation ever be appropriate for `POST /v1/attest`, or is per-device identity (current model) actually required by the anti-theft use case? (AT itself used the platform's EPID only to prove "genuine Intel platform," not device identity — identity rode in the encrypted payload.)
5. Does any shipping Intel platform still expose an AT-style hardware rendezvous timer usable by third parties, or did AT's 2015 EOL remove the last consumer path to ME-enforced shutdown — making PBL's UEFI-level BLOCK the strongest available enforcement?
