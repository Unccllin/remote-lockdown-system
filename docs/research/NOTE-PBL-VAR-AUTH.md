# NOTE-PBL-VAR-AUTH — Authenticated-variable options for PBL's shell-writable variables (NG-R2)

> **Scope:** Resolves wayfinder ticket `NG-R2` (`docs/wayfinder/tickets/NG-R2-variable-authentication.md`). Finding F2 (`SYNTHESIS-NEXT-GEN-DESIGN.md` §2): `PblMarkerTest`, `PblBootmgrSvn`, and `MemoryOverwriteRequestControl` are written via plain `gRT->SetVariable` and are therefore spoofable/erasable by any reachable UEFI shell (`setvar`, `dmpstore -d/-l`). This note answers, per variable: (1) can it carry `EFI_VARIABLE_AUTHENTICATED_WRITE_ACCESS` or `EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS`, and with what key-enrollment prerequisite; (2) whether the spec-defined MOR variable can be authenticated without breaking OS use; (3) which alternative hardening (TPM-sealed state, PCR-extended evidence, advisory-only digest coverage, signed ESP policy blob) fits where authentication is impossible. Output: the per-variable table that becomes the fix ticket's implementation spec.

## Mechanism recap — what the local edk2 actually enforces

1. **Counter-based `EFI_VARIABLE_AUTHENTICATED_WRITE_ACCESS` is dead.** The attribute is marked deprecated/reserved in `UefiMultiPhase.h:31–33`, and `ProcessVariable` returns `EFI_UNSUPPORTED` for any write carrying it (`AuthService.c:1012–1016`). Per-variable answer for all three variables: **AW is not viable anywhere**; the only real option is `EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS` (TBA).

2. **TBA write format** (`AuthService.c:2104–2212`): the `SetVariable` Data buffer must be `EFI_VARIABLE_AUTHENTICATION_2` (EFI_TIME timestamp with Pad1/Nanosecond/TimeZone/Daylight/Pad2 all zero) + `WIN_CERTIFICATE_UEFI_GUID` (`wCertificateType = WIN_CERT_TYPE_EFI_GUID`, `CertType = EFI_CERT_TYPE_PKCS7_GUID`) + PKCS7 SignedData + the new variable value. The signature covers the serialization `(VariableName, VendorGuid, Attributes, TimeStamp, Data)` (ll. 2221–2258). The descriptor is stripped on write; `GetVariable` returns only the payload. Digest must be SHA-256/384/512. Timestamps must strictly increase across non-append writes — replay is rejected (ll. 2126–2133). PBL gets timestamps from `gRT->GetTime`.

3. **Private (non-PK/KEK/db) authenticated variables need NO key enrollment in PK/KEK/db.** Any variable other than the Secure Boot key variables takes the `AuthVarTypePriv` path (`AuthVariableLib.c:431–432` → `AuthService.c:2364+`). On the **first** TBA write (variable absent or never authenticated, `OrgTimeStamp == NULL`), the firmware only checks that the PKCS7 signature is cryptographically valid — a **self-signed signer cert is acceptable** — then `InsertCertsToDb` records hash(signer-cert CN + top-level-issuer TBS) in the `certdb` variable, keyed by `(VariableName, VendorGuid)` (ll. 2434–2448). On **subsequent** writes, the signer chain must match the certdb entry (ll. 2386–2419) and the timestamp must be newer. **The vendor GUID is arbitrary** — a custom PBL GUID works identically to `EFI_GLOBAL_VARIABLE` for TBA purposes; certdb is keyed by name+GUID, not by GUID family.

4. **Once a variable is TBA, unauthenticated writes are refused** with `EFI_WRITE_PROTECTED` (ll. 1032–1039). This is the shell-spoofing fix: `setvar`/`dmpstore -l` cannot forge the PKCS7 signature.

5. **Three caveats that bound the protection:**
   - **Deletion is weaker than write-protection.** `IsDeleteAuthVariable` + `ProcessVariable` (ll. 900–936, 986) allow deletion of a *common* authenticated variable when `UserPhysicalPresent()` OR `!IsVariablePolicyEnabled()`. `UserPhysicalPresent()` is platform-defined (`PlatformSecureLib`); on platforms with VariablePolicy disabled, unsigned deletion is allowed outright. After deletion an attacker can recreate the variable unauthenticated or under their own cert. **Consequence: TBA is spoof-resistance, not guaranteed existence.** Readers must fetch `Attributes` in `GetVariable` and treat a non-TBA instance as untrusted; absence must stay a defined state.
   - **Squatting.** If an attacker creates the variable TBA under *their* cert before PBL's first write, PBL's writes fail `EFI_SECURITY_VIOLATION` (cert mismatch vs certdb), and deletion may be blocked (needs physical presence or VariablePolicy-off). Mitigation: first TBA write must happen at provisioning/first-boot before the attack window; PBL must degrade gracefully rather than hard-fail if it can't claim the variable.
   - **Unauthenticated squat does NOT block.** A pre-existing *plain* variable has `TimeStamp == NULL` → the TBA write takes the first-write path and binds PBL's cert (ll. 2434). Note the spec/shell rule that attributes can't be changed on an existing variable (STUDY-UEFI-SHELL l. 69): portable code should delete-then-recreate rather than rely on attribute upgrade.

6. **The signing key is the real deployment problem.** `Pkcs7Sign` in this tree is RSA-only (`CryptPkcs7Sign.c:117`), while PBL's pinned policy key is EC P-256 (`gen-policy-rot.py`, `PolicyRootOfTrust.c`) — so the policy key cannot produce the AUTH2 PKCS7 directly. Worse, **a private key embedded in `PblApp.efi` is not secret**: the ESP is readable by any UEFI shell or OS process, so an embedded key can be extracted and used to forge "authenticated" writes. Options that keep the key off the readable ESP:
   - **Offline-signed AUTH2 payloads carried inside the signed `policy.cose` blob.** The var-signing key (a dedicated RSA key) stays server-side. The server emits `EFI_VARIABLE_AUTHENTICATION_2`+PKCS7+payload blobs with monotonically increasing timestamps; PBL's job is just `SetVariable` of the delivered blob. No private key on-device; update cadence = policy update cadence. Fits variables whose content changes only on policy changes.
   - **TPM-sealed/TPM-NV-resident key.** Provision a per-device var-signing key whose private half lives in a TPM NV index (or sealed blob) with a policy PBL satisfies only in its execution context. Heaviest option; PBL already has TPM NV/session infra (`TpmClient.c`, `TpmSession.c`, `Override.c`).
   - If neither is warranted, the variable shouldn't be a variable at all — see alternatives in §3.

7. **Read-side authentication does not exist here.** `EFI_VARIABLE_ENHANCED_AUTHENTICATED_ACCESS` (UEFI 2.5+ read-auth) is absent from this edk2 tree; every variable is readable by anyone. Integrity must therefore live in either TBA-write + attribute checks, TPM/PCR evidence, or digest coverage.

## Findings specific to PBL's three variables

8. **`Mor.c` and `PlatformState.c` use the wrong GUID — PBL's MOR is currently a decoy.** Both write and read `L"MemoryOverwriteRequestControl"` at `EFI_GLOBAL_VARIABLE` (`Mor.c:18,21,49–55,66–72`; `PlatformState.c:590–596`), but the TCG spec puts MOR at `gEfiMemoryOverwriteControlDataGuid` = `e20939be-32d4-41be-a150-897f85d49829` (`MemoryOverwriteControl.h`, `MdePkg.dec:513`). PBL today creates/reads a same-named variable in the *global* namespace that the real TcgMor driver never looks at: `PblRequestMor()` is a no-op for actual memory clearing, and `MorRequested` (Decision.c:248) reads a value nobody honors — which is exactly the spoofable state F2 describes, except the spoof is *built in*. This must be fixed regardless of the auth decision.

9. **`Mor.c`'s "bit 1 = MOR lock" is not the spec lock.** `MemoryOverwriteControl.h` defines bit 0 (ClearMemory) and bit 4 (`MOR_DISABLEAUTODETECT_BIT_MASK` = 0x10). There is no bit-1 lock inside MOR; locking lives in the *separate* variable `MemoryOverwriteRequestControlLock` at `gEfiMemoryOverwriteRequestControlLockGuid` (`MemoryOverwriteRequestControlLock.h`; semantics in `TcgMorLockSmm.c:164–320`).

10. **`PblBootmgrSvn` is never written in this repo.** `Svn.c` only reads it ("if set by firmware or a prior PBL run", ll. 25–26). It sits at `EFI_GLOBAL_VARIABLE` (l. 18) despite the `Pbl` prefix — it occupies the shared global namespace and is `dmpstore`-visible/writable by default. As a rollback-detection input its *content* is security-relevant (a forged low/high SVN feeds `State->BootmgrSvn`, `PlatformState.c:906`), but no in-repo writer exists to authenticate; if platform firmware writes it, that firmware will not sign for PBL's certdb.

11. **`PblMarkerTest` is diagnostic-only.** Written by the standalone `MarkerTest.inf` app (custom `mPblMarkerGuid`, NV|BS|RT) and read by nothing in the decision path. Its integrity matters only if it is ever used as a "did PBL execute" canary.

## Q1 — key-enrollment prerequisites (answer)

- `AUTHENTICATED_WRITE_ACCESS` (counter-based): **no** — deprecated attribute, `EFI_UNSUPPORTED` in edk2 (and likely on shipping firmware).
- `TIME_BASED_AUTHENTICATED_WRITE_ACCESS`: **yes** for any PBL-owned variable at any vendor GUID. **No PK/KEK/db enrollment required** — private variables use the `certdb` trust-on-first-write model; a self-signed signer cert is sufficient. Prerequisites that *do* exist: (a) a valid `EFI_VARIABLE_AUTHENTICATION_2`+PKCS7 blob per write (SHA-256+ digest, zeroed timestamp subfields, strictly increasing `EFI_TIME`); (b) a signing key PBL can use at write time — which is the hard part because the ESP is world-readable, so **the private key must not live in `PblApp.efi`**; the recommended pattern is offline-signed AUTH2 payloads delivered inside signed `policy.cose`, with the RSA var-signing key held server-side (reuse `gen-policy-rot.py`-style provisioning; note `Pkcs7Sign` is RSA-only in this edk2); (c) the variable must be claimed before an attacker squats it authenticated (provisioning-time first write); (d) readers must verify the TBA attribute on `GetVariable` and treat non-TBA/absent as untrusted, because deletion protection is platform-dependent (`UserPhysicalPresent` / VariablePolicy).

## Q2 — MOR (answer)

MOR **cannot** be authenticated without breaking the OS: it is spec-defined as an unauthenticated firmware-created variable that Windows sets unauthenticated, and EDK II's SMM variable-check handler hard-codes `Attributes == NV|BS|RT` and `DataSize == 1` — a TBA write fails before it reaches auth processing. Making it TBA first would also block all later OS writes. The spec's own hardening is the companion `MemoryOverwriteRequestControlLock` variable (lock-without-key `0x01` or v2 8-byte key): once written, MOR writes are denied until reboot — that is the correct anti-`dmpstore` control, on SMM-capable platforms. Where SMM MorLock is absent, MOR stays advisory; PBL must not treat MOR-write-success as guaranteed. Separately: **PBL must move its MOR access off `EFI_GLOBAL_VARIABLE` onto `gEfiMemoryOverwriteControlDataGuid`** — the current code operates on a decoy.

## Q3 — alternatives where auth is impossible (answer)

- **TPM-sealed/NV state**: best fit for state that must be *secret or write-protected* and PBL-written (e.g., a var-signing key, override counters). PBL already has the TPM client/session/NV machinery. Heavier than needed for all three current variables.
- **PCR-extended evidence**: best fit for "did X happen / what was measured" markers — `PblMarkerTest`'s canary use, and bootmgfw identity (hash already flows into PCR 13 inputs). Shells can extend PCRs forward but cannot unextend, and server quotes detect forgery.
- **Advisory-only digest coverage**: right default for anything read from an unauthenticated variable that can't be moved — feed the value into the PCR-13 inputs digest and let `Decision.c` weigh it, never as sole gate. Applies to `PblBootmgrSvn` if the var read is retained, and to `MorRequested` until the GUID fix lands.
- **Signed ESP policy blob (`policy.cose`)**: right home for *expectations* (SVN floor, MOR-required flag) and for *delivering* offline-signed AUTH2 update payloads. Root of trust already pinned at build time.
