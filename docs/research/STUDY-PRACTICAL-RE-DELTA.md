## One-paragraph technical overview

Chapter 3 is the payload for this system: it explains exactly where the Windows kernel keeps its asynchronous-execution bookkeeping and how rootkits exploit it. Every stealth/persistence mechanism an adversary would deploy against the agent lives in a small set of enumerable structures — the per-CPU `KPRCB` (DPC queues `DpcData[2]`, `TimerTable`, `DpcStack`), the per-NUMA-node `ENODE.ExWorkerQueues[7]` (work items), per-thread `KTHREAD.ApcState.ApcListHead[2]` (kernel/user APCs), the three global notify-routine arrays (`PspCreateProcessNotifyRoutine`, `PspCreateThreadNotifyRoutine`, `PspLoadImageNotifyRoutine` + `PspNotifyEnableMask`), `PsLoadedModuleList`/`PsActiveProcessHead` (DKOM unlink targets), and the syscall plumbing (`KeServiceDescriptorTable`/`KiServiceTable`, `IA32_LSTAR` MSR, IDT). The book's rootkit walk-throughs show the concrete attack patterns: SSDT patch via MDL-remapped writable view (no CR0 write needed), process-hiding by `ActiveProcessLinks` unlink, kernel→user code injection by queuing a user-mode APC, and file deletion via a hand-crafted `IRP_MJ_SET_INFORMATION`/`FileDispositionInformation` IRP that bypasses syscall hooks entirely. Chapter 4 shows the debugger's side: software breakpoints are `0xCC` byte patches (integrity-check detectable), hardware breakpoints use DR0–DR7 (invisible to hashing), and `sxe ld:` breaks on module load. Chapter 5 formalizes obfuscation: pattern substitution, constant unfolding, dead/junk code, opaque predicates, CFG flattening, VM protection, SEH-as-anti-debug — and the Barak impossibility result that no general virtual-black-box obfuscator exists, so obfuscation is a delay mechanism, never a confidentiality guarantee.

## Key technical facts / mechanisms (delta only)

### Kernel enumeration & stealth primitives (adversary toolkit)

1. **The `KPCR`/`KPRCB` is the root of per-CPU kernel introspection.** On x64, `gs:[0]` = PCR and `gs:[0x188]` = `KPRCB.CurrentThread` (this is literally how `PsGetCurrentThread` is implemented); on x86 it's `fs:[0x124]`; on ARM it's coprocessor 15 (`MRC p15,0,R3,c13,c0,3`). `KPRCB` holds `DpcData[2]` (two `KDPC_DATA` queues — normal and threaded DPCs), `DpcStack`, `MaximumDpcQueueDepth`, `TimerTable` (`KTIMER_TABLE`: `TimerExpiry[64]` + `TimerEntries[256]`), and `ParentNode → _KNODE/_ENODE`. Offsets are version-specific (Win8 x64: `DpcData` at +0x2D80, `TimerTable` at +0x2E00, `ParentNode` at +0x5338). (pp. 89–91, 130, 136–140)

2. **SSDT structure and encoding.** `KSERVICE_TABLE_DESCRIPTOR { Base, Count, Limit, Number }`; `KeServiceDescriptorTable` holds the native table, `KeServiceDescriptorTableShadow` additionally holds the GUI (`W32pServiceTable`) table. `KeServiceDescriptorTable` is exported on x86 but **not** on x64. On x64/ARM, `KiServiceTable` entries are 32-bit values: the syscall offset is in the **top 20 bits** (`value >> 4`, added to `KiServiceTable`) and the **low 4 bits** encode the number of stack-passed arguments. Syscall number = index; on x64, bit 12 of the syscall number (`eax` shifted: `edi=(eax>>7)&0x20`) selects native vs. GUI table. (pp. 92–94, 99–100)

3. **Two ways to write read-only kernel memory.** (a) Toggle `CR0.WP` (bit 16): `mov eax,cr0; and eax,0xFFFEFFFF; mov cr0,eax` — the classic pattern, flagged by PatchGuard-era monitoring. (b) **MDL remapping** — no CR0 write: `IoAllocateMdl` → `MmProbeAndLockPages` → `MmMapLockedPagesSpecifyCache` produces a *second, writable* virtual mapping of read-only pages (a kernel-mode `VirtualProtect`). Sample A hooks the SSDT by MDL-mapping `KiServiceTable`, raising IRQL to `DISPATCH_LEVEL`, then swapping entries with user-supplied addresses via an IOCTL. On x64/ARM, Kernel Patch Protection (PatchGuard) bugchecks on hook/modification of security-critical structures — which pushes attackers toward data-only attacks (callback arrays, list unlinking) rather than code patches. (pp. 107, 153–155, 169–171)

4. **DKOM via list unlinking.** `EPROCESS.ActiveProcessLinks` is a `LIST_ENTRY`; overwriting its `Flink`/`Blink` neighbors removes a process from `NtQuerySystemInformation`/Task Manager enumeration while it keeps running. `PsLoadedModuleList` (kernel module list, `KLDR_DATA_TABLE_ENTRY` with `LIST_ENTRY` at offset 0) is reachable on XP via `KPCR+0x34` (`KdVersionBlock`) `+0x70`; drivers use the same list to locate `ntoskrnl` base or unlink their own driver entry. `LIST_ENTRY` ops are always inlined — `InitializeListHead`/`InsertHeadList`/`RemoveEntryList` never appear as calls; recognition is by the Flink@+0/Blink@+4or8 store pattern. `CONTAINING_RECORD` converts a `LIST_ENTRY*` back to the host struct. (pp. 108, 111–121)

5. **Process/thread/image notify callbacks are post-hoc and attackable.** `PspInitializeCallbacks` creates three global arrays (`PspCreateProcessNotifyRoutine`, `PspCreateThreadNotifyRoutine`, `PspLoadImageNotifyRoutine`); a global flag `PspNotifyEnableMask` gates delivery; `PspInsertThread`/`PspExitThread` invoke them. Weaknesses the book's exercises spell out: callbacks fire **after** creation (code runs first); manual mapping / process hollowing never triggers `PsSetLoadImageNotifyRoutine` (it fires only for the normal PE loader path); the fixed-size arrays themselves are a DKOM target — an attacker can overwrite entries to blind EDR. `ObRegisterCallbacks` and `CmRegisterCallback` provide analogous object/registry interception. (pp. 142–143)

6. **APCs are the canonical kernel→user injection vector.** A `KAPC` holds `Thread`, `ApcListEntry`, `KernelRoutine` (runs at `APC_LEVEL`, kernel mode), `RundownRoutine` (thread exit), `NormalRoutine` (runs at `PASSIVE_LEVEL` in `ApcMode` — kernel or user). `KeInitializeApc` + `KeInsertQueueApc` queue it into `KTHREAD.ApcState.ApcListHead[0]` (kernel) or `[1]` (user). User APCs fire only when the target thread is **alertable**. Thread suspension is implemented as a kernel APC (`KTHREAD.SchedulerApc` → `KiSchedulerApc` waits on `SuspendEvent`); `KTHREAD.ApcQueueable` disables queueing. Rootkits queue user-mode APCs into a victim thread to get ring-3 code execution inside a chosen process — MoonBounce-style staging (cf. STUDY-UEFI-BOOTKITS). (pp. 131–135)

7. **DPCs run at `DISPATCH_LEVEL` in arbitrary thread context.** `KDPC` = `{Type, Importance, Number, DpcListEntry, DeferredRoutine, DeferredContext, SystemArgument1/2, DpcData}`; `KeInitializeDpc` + `KeInsertQueueDpc` enqueue into the current or targeted CPU's `KPRCB.DpcData` queue (`KeSetTargetProcessorDpc`, `KeSetImportanceDpc`). At `DISPATCH_LEVEL` a DPC cannot wait, cannot take a page fault, and cannot touch paged pool — code+data must be non-paged resident. The `DpcWatchDogTimer` bugchecks `0x133` (`DPC_WATCHDOG_VIOLATION`) on a long-running DPC. Rootkits use DPCs as the safe point to mutate global lists (e.g., `ActiveProcessLinks` unlink) because the queue is spin-lock protected per CPU. (pp. 135–141)

8. **Timers are a stealthy recurring-execution primitive.** `KTIMER {Header, DueTime, TimerListEntry, Dpc, Processor, Period}`; `KeSetTimer`/`KeSetTimerEx` insert into the current processor's `KPRCB.TimerTable` (256 hashed `TimerEntries` + `TimerExpiry[64]`). On each clock interrupt the kernel checks the table and requests a DPC interrupt; `KiTimerExpiration`/`KiExpireTimerTable` remove the `KTIMER` and `KeInsertQueueDpc` the associated DPC — which is why an enumerated timer's `Dpc` pointer can look "inconsistent" (the `KDPC`'s `DpcListEntry` is now linked into the DPC queue, not the timer). `KeCancelTimer` removes unexpired timers. A periodic timer + DPC is a lightweight "every N minutes, run this" persistence that never appears in a thread list. (pp. 110, 140–141; pre-exercise `ch3_timer_enumeration.c`)

9. **Work items execute at `PASSIVE_LEVEL` in the System process via `ExpWorkerThread`.** `IoAllocateWorkItem`/`IoQueueWorkItem` enqueue an `IO_WORKITEM`/`WORK_QUEUE_ITEM` onto `ENODE.ExWorkerQueues[7]` (per-NUMA-node array covering `CriticalWorkQueue`/`DelayedWorkQueue`/`HyperCriticalWorkQueue` priorities). Work items are the standard escape hatch from a DPC: a DPC can't call `PsCreateSystemThread` or wait (needs `< DISPATCH_LEVEL`), so it queues a work item that reuses pooled system threads. This also means a hostile DPC can launder privileged work into System-context threads. (pp. 129–131)

10. **Execution-context rules determine what kernel code can see.** `DriverEntry` → System context; IOCTL dispatch → *requesting thread's* context; APC → *target thread's* context; DPC/timer → arbitrary context; work item and `PsCreateSystemThread(NULL ProcessHandle)` → **System process (PID 4), not the caller**. `KeStackAttachProcess` switches a thread into another process's address space. This is why the `ch3_thread_context.c` exercise matters: kernel code that assumes "current process = caller" is wrong, and adversary code explicitly picks its context. (pp. 109–110, 128–129)

11. **Syscall entry plumbing is a hook surface independent of the SSDT.** x64 `SYSCALL` jumps to `MSR IA32_LSTAR (0xC0000082)` = `KiSystemCall64` (set early by `KiInitializeBootStructures`); x86 `SYSENTER` jumps to `MSR 0x176` = `KiFastCallEntry` (return via `SYSEXIT` → `EIP=EDX`, `ESP=ECX`); legacy `int 2e` goes through IDT entry `0x2e` = `KiSystemService`. User-mode stubs reach the dispatcher via `KUSER_SHARED_DATA` (always mapped at `0x7ffe0000`; `SystemCall`/`SystemCallStub` at `+0x300`/`0x7ffe0300`). An attacker can swap the MSR target or IDT entry rather than patch `KiServiceTable` — a different signature class. (pp. 96–102)

12. **IRP stack mechanics enable syscall-bypassing I/O.** An `IRP` is a static header plus an array of `IO_STACK_LOCATION`s; the "next" stack location is the element **above** the current one, so optimized x64 code sets it with negative offsets (e.g., `[rcx-0x48]` = next location's `MajorFunction`). `IoGetCurrent/NextIrpStackLocation` and `IoSetCompletionRoutine` are `FORCEINLINE` — they never appear as call sites, only as field writes (`Tail.Overlay.CurrentStackLocation`, `CompletionRoutine` @ +0x38 on x64). Sample B crafts a raw `IRP_MJ_SET_INFORMATION`/`FileDispositionInformation` IRP (`IoAllocateIrp` + manual stack-location fill + completion routine + `IoCallDriver` to the filesystem device) to delete a file without touching `ZwDeleteFile` — defeating syscall-level deletion hooks. Completion routines also let a filter/rootkit rewrite a lower driver's return buffer before it reaches user mode. (pp. 143–146, 174–178)

13. **IOCTL buffering methods define a security gradient.** `CTL_CODE = (DeviceType<<16)|(Access<<14)|(Function<<2)|Method`. `METHOD_BUFFERED`: kernel validates the user buffer and copies it to a non-paged `AssociatedIrp.SystemBuffer` (safest, most common in software drivers). `METHOD_IN/OUT_DIRECT`: kernel builds + locks an MDL (`MdlAddress`) over the user buffer (fast for big transfers). `METHOD_NEITHER`: **zero validation** — raw user pointer arrives via `Parameters.DeviceIoControl.Type3InputBuffer`; the classic source of kernel corruption/disclosure bugs. Third-party `DeviceType`/`Function` values ≥0x8000/≥0x800 are conventions, not enforcement. (pp. 150–153)

14. **Driver anatomy = the detection checklist.** `DRIVER_OBJECT {DeviceObject, DriverStart, DriverSize, DriverSection(→loaded-module list entry), DriverInit(→entry), DriverUnload, MajorFunction[IRP_MJ_MAXIMUM+1]=28 dispatch slots}`; `IoCreateDevice` allocates a `DEVICE_OBJECT` with a non-paged `DeviceExtension`; `IoAttachDevice` builds device stacks so filter drivers see a target's IRPs first; `\DosDevices\X` = `\??\X` symlink for user reachability; no `DriverUnload` = resident forever (typical rootkit). The book's RE checklist — find `DriverEntry`, dispatch table, attached devices, device extension, IOCTLs, then DPCs/work items/APCs/timers/callbacks — is exactly the audit list for evaluating a hostile or protective driver. (pp. 146–150, 156–159)

### Debugging mechanics (how the adversary inspects/defeats the agent)

15. **Software breakpoints are byte patches; hardware breakpoints are register state.** `bp` writes `0xCC` (single-byte `INT3`) over the target byte — visible to any code-integrity/self-hash check; note `INT3` also has a two-byte form `CD 03` with different Windows dispatch behavior (exercise 20). `ba` (hardware/data breakpoint) programs `DR0–DR7` — architecturally limited to 4, leaves code bytes untouched, **invisible to hashing**; detection requires reading DR registers or noticing `#DB` timing. `bu` defers resolution to module load; `bp /p <EPROCESS>` scopes a breakpoint to one process (kernel debugger). (pp. 183–184, 208–211)

16. **Kernel debugger capabilities define the attacker ceiling.** `sxe ld:drivername` breaks into KD when a driver loads — so a debug-enabled boot lets an adversary freeze the system at *any* protective driver's entry point, then use `!process`, `!thread`, `!pcr`, `!devobj`, `!drvobj`, `dt nt!_*` to enumerate everything in facts 1–8 above and patch decisions in memory. DbgEng is scriptable (pseudo-registers, aliases, script files, C++/MASM expression evaluators) and extensible (custom extension DLLs; `cdb -z` maps a PE or crash dump for static analysis; `windbg -I` installs it as the JIT postmortem debugger). `KUSER_SHARED_DATA`/PEB fields (`PEB.BeingDebugged` at offset +0x2) are the classic user-mode debugger detection. (pp. 183–184, 188–211, 216–265, and `!for_each_*` extension commands p. 239)

### Obfuscation / anti-analysis (protecting the agent; detecting packed tampering)

17. **Data-based obfuscation primitives.** Constant unfolding (replace a constant with a computation — inverse of constant folding), dead-code/junk insertion (inverse of dead-code elimination; requires liveness knowledge), arithmetic identities (`x^0xFFFFFFFF = NOT`, `-x = ~x+1`, rotates as shift pairs), pattern-based substitution (hundreds of hand-written semantic-preserving templates applied iteratively — one `push` can balloon into millions of instructions; the subtlety is **flag liveness**: `sub`-for-`push` substitutions are only safe where flags are dead). (pp. 269–278)

18. **Control-based obfuscation primitives.** Function in/out-lining to break the call graph; unconditional-jump chains destroying sequential/temporal locality (semantically trivial, manually exhausting); `push+ret` = `jmp`, `call`-as-jmp with discarded/faked return addresses, `cmov`-selected return addresses = conditional jumps; **OS-based indirection** — SEH/VEH/unhandled-exception handlers as control flow: raise a fault, handler rewrites the thread context's EIP (doubles as anti-debug: a debugger must pass exceptions faithfully or the target's behavior changes and tampering is revealed); **opaque predicates** (Collberg): always-true/always-false (`P_t`/`P_f`) branches that inject dead CFG edges — best when tied to program state; `P_?` randomized predicates require both branches be semantically equivalent clones (diamonds); **CFG flattening**: replace control structure with a dispatcher `switch` + explicit state variable — "partial virtualization of control flow only"; **VM protection** (VMProtect, Code Virtualizer): interpreter + custom bytecode, selective per-function due to CPU cost. (pp. 278–286)

19. **Nanomites-style self-debugging is the strongest anti-debug composition in the book.** The protector *is* the debuggee's debugger: conditional jumps are replaced by `INT3`s that the attached protector handles and emulates; detaching the debugger crashes the target because exceptions no longer get handled. (Armadillo "nanomites"; Deroko implementation.) (pp. 282–283)

20. **No virtual-black-box obfuscator exists (Barak et al.); white-box crypto leaks.** A probabilistic obfuscator `O` satisfying the VBB property (analyst learns nothing beyond oracle access to `P`) cannot exist for all programs; white-box DES/AES (Chow: cipher as a network of randomized, input/output-encoded lookup tables embedding round keys) has been cryptanalyzed (Goubin for DES, Billet for AES). Security-by-obscurity is like cipher rounds — each layer is weak, iteration accumulates strength — but it only *raises the time-to-break*; a defender wins by rotating protections faster than the attacker breaks them. (pp. 286–289)

21. **Deobfuscation = compiler optimization run in reverse, plus hybrid analysis.** Constant folding undoes unfolding; dead-statement elimination removes junk; peephole optimization inverts pattern substitution (automated construction of both obfuscator and peephole engines is published: Jacob et al., Bansal); opaque-predicate breaking corresponds to *completeness* in the abstract-interpretation model (Dalla Preda & Giacobazzi). Symbolic execution (symbolic store + path constraint + SMT/SAT solver) explores paths; **concolic execution** substitutes concrete values when constraints are too complex — the practical recipe for VM-protected code: break on each VM entry, dump memory, seed symbolic state from the dump, then symbolically execute the handler trace. (pp. 289–295, 333–334)

22. **Tools and the packer-detection insight.** Metasm (Ruby): `code_binding` computes the semantic binding of a basic block — register/memory expressions that make VM handlers readable. Miasm: IR-based framework for packer/VM analysis. **VxStripper** instruments QEMU's TCG DBT (inject `op_callback` per translation block; translate TCG→LLVM for normalization); its unpacking module compares each translation block in guest memory against the on-disk file — the first divergent block marks the original entry point — and rebuilds the PE by restoring OEP, reconstructing IAT + relocations (via traced Win32/native API calls and load/store instrumentation), and consistency-checking headers. **Corollary for defense: a packed/runtime-unpacked binary characteristically has a rebuilt IAT, regenerated `.reloc`, patched entry point — cheap static signals of packing.** (pp. 295–312)

23. **PE parsing is thin in this book, but the canonical parse chain appears in a DbgEng script.** `@$peb→ImageBaseAddress` → `IMAGE_DOS_HEADER.e_lfanew` → `IMAGE_NT_HEADERS` → `FileHeader.SizeOfOptionalHeader` → first `IMAGE_SECTION_HEADER` (`VirtualAddress`/`VirtualSize` per section; `OptionalHeader.SizeOfImage` bounds). This is the minimal chain any PE integrity/validator implements — it maps directly to a future `ChainLoad.c` section-level check or an agent-side self-image parser. (pp. 250–252)

24. **ARM notes (only if the agent ports).** Windows on ARM uses `SVC` (a.k.a. `SWI`) with the syscall number in `R12` → `KiSWIException` via the exception vector table (base `0x0` or `0xFFFF0000` per CP15 V bit); kernel current-thread via `MRC p15,0,R3,c13,c0,3`, user TEB via `c13,c0,2`; breakpoints via `BKPT` or architecturally-undefined encodings; atomics via `LDREX/STREX` + `DMB/DSB/ISB` barriers; kernel/user split is 2GB/2GB with the same `MmSystemRangeStart`/`MmHighestUserAddress` symbols. Everything else in facts 1–14 (DPC/APC/timer/callback model) is arch-independent kernel design. (pp. 68–70, 89, 102–103, 109)

## New capabilities this suggests

1. **Kernel-mode tamper-evidence companion driver (future, optional).** The `ch3_*` exercises are a blueprint for a small defensive driver that snapshots and attests: `PspCreateProcessNotifyRoutine`/`PspCreateThreadNotifyRoutine`/`PspLoadImageNotifyRoutine` array contents (facts 5), per-CPU DPC/timer queues and APC queues (facts 1, 6–9), `PsLoadedModuleList` vs. `PsActiveProcessHead` cross-walk to catch DKOM-hidden processes and unlisted drivers (fact 4), `KiServiceTable` entry ranges (each entry must resolve inside the `ntoskrnl`/`win32k` image — fact 2), `IA32_LSTAR`/`SYSENTER_EIP` MSRs and IDT integrity (fact 11), and `CR0.WP` state (fact 3). Digest → sign → include in the agent's checkin/`tamper_detected` evidence. Caveat the book states repeatedly: all offsets are version-specific and PatchGuard-hostile — enumerate *structures*, don't patch.

2. **Agent self-integrity check that understands breakpoint mechanics.** A Python-level periodic check that hashes the running agent's own code/bytecode files (and, for a frozen/PyInstaller exe, its `.text` section via the fact-23 parse chain) catches `0xCC` software breakpoints and code patches. It cannot catch DR0–DR7 hardware breakpoints or a debugger that merely reads — pair it with timing/heartbeat anomalies and `PEB.BeingDebugged`/`CheckRemoteDebuggerPresent`-style checks if the agent is ever compiled. On Windows, this maps to a `tamper_protection` module upgrade beyond the current stub (`agent.py:142-154`).

3. **Treat kernel-visible state as advisory, not authoritative.** Facts 5–7 and 12 explain *why*: notify callbacks fire post-facto and are bypassable/removable; APC injection and crafted IRPs act below any user-mode filter. Design rule for the agent: any signal obtainable only through the kernel (process lists, module lists, file APIs) can be forged by a sufficiently privileged adversary; the trustworthy anchors remain TPM-sealed state, PBL's pre-boot platform digest, and server-side verdicts. This hardens the `startup_check` sentinel logic (`agent.py:2697+`) — re-assertion is the right pattern because local state *will* lie under a rootkit.

4. **IOCTL contract hardening for any future agent↔driver channel.** If capability 1 ever ships, its user↔kernel interface must use `METHOD_BUFFERED` (validated `SystemBuffer`), never `METHOD_NEITHER`/`Type3InputBuffer` (fact 13), with `FILE_READ_DATA`-class access bits and strict IOCTL-code validation — the book's Sample-A IOCTL (`0x22C004`, `FILE_DEVICE_UNKNOWN`, `METHOD_BUFFERED`) is the attacker's template for what the channel will face.

5. **Packed/evasive-binary detection on the protected system.** Fact 22's unpacking mechanics invert into cheap static signals for the agent's filesystem sweep: entry point outside/in the last section, tiny or synthetic IAT, rebuilt `.reloc`, missing certificate table on a nominally "signed-looking" binary, high-entropy sections. Useful both for detecting tampered ESP binaries *and* for recognizing when a protected system's tools were replaced by packed copies.

6. **Calibrated expectations for protecting the agent itself.** Facts 17–21 bound what obfuscation buys: iterated layers (junk code, opaque predicates, CFG flattening, string/constant encoding of URLs and policy blobs, SEH-based control flow) raise time-to-break from hours to days/weeks — worth applying to the decision/persistence logic — but Barak impossibility + broken white-box crypto mean **no secret can live inside the agent binary**. This validates the existing architecture: keys stay server-side or TPM-sealed; the agent is intentionally expendable code whose real enforcement is the deadman + server + pre-boot lock triangle.

7. **ARM contingency note.** If the agent ever targets Windows on ARM (or a future PBL-AARCH64 build), fact 24 is the syscall/debugger map; the kernel callback/DPC/APC model (facts 1–10) carries over unchanged, but all `KPRCB`/structure offsets and the `SVC`/`KiSWIException` entry differ — the enumeration drivers would need ARM-specific offset tables.
