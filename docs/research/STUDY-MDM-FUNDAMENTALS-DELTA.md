## One-paragraph technical overview

Windows MDM is a two-sided contract: the OS ships with an **OMA-DM** protocol engine (XML, Open Mobile Alliance) and a fixed set of **Configuration Service Providers (CSPs)** — per-feature "mini-receivers" that accept policy XML and effect change — and any MDM service (Intune, Workspace ONE, MobileIron) is just a cloud front-end that talks OMA-DM to those CSPs. Enrollment is a two-step process (Azure AD device identity *then* MDM enrollment, chained by "auto-enrollment"); device identity can be as weak as a user credential (user-driven join) or as strong as a TPM 2.0 attestation handshake bound to a pre-registered **hardware hash** (Autopilot self-deploying mode). Management after enrollment is: groups → assigned profiles (CSP settings) → device-initiated sync (~3 min for first 30 min, then ~6–8 h steady state) → per-setting status reporting (Conforms / Not Applicable / Pending / Conflict). Device actions are tiered — Retire (unenroll), Wipe (± retain enrollment, "protected" variant can't be stopped), Autopilot Reset (preserves enrollment, 45-min warning), Fresh Start — plus BitLocker with **recovery-key escrow to Azure AD gated before encryption starts**, and a compliance pipeline that feeds SGRA/Defender health attestation into Conditional Access token-grant decisions. Everything in this model executes only inside a live, enrolled, online Windows — which is precisely the gap this repo's pre-boot lockdown fills.

## Key facts / mechanisms (delta from existing STUDY notes — all nine prior notes are firmware/TPM-focused; this is the first MDM-stack note)

### Enrollment & device identity

1. **MDM enrollment is two distinct steps, and conflating them is the classic failure.** "Workplace Join" (Azure AD *registered*) gives SSO only — no management; full enrollment requires the separate MDM-enroll step, normally chained automatically by "MDM auto-enrollment" (an Azure AD Premium P1/P2-only feature) (PDF pp. 51, 74–76). Admin-vs-standard-user enrollment also differs: only local admins get the "Join this device to Azure Active Directory" option (PDF p. 77).
2. **All MDM vendors are capped by the same CSP list.** Microsoft decides what is manageable; "no single MDM system can fundamentally manage Windows better than any other" — differentiation is UI surfacing ("first-class" vs. "third-class"/custom-OMA-URI settings) and bolt-on agents delivered via the MSI CSP (Intune Management Extension for PowerShell/Win32, polling hourly and non-configurable) (PDF pp. 45–46, 250).
3. **Autopilot device identity = a pre-registered hardware hash.** A ~4 KB "hardware ID"/"hardware hash" (Device Serial Number + Windows Product ID + Hardware Hash CSV columns; harvested via `Get-WindowsAutopilotInfo`, ≤175 devices per upload) is pre-stuffed into the tenant by IT/OEM/reseller; at OOBE the machine phones the Autopilot service, matches the hash, and enrolls (PDF pp. 328–334, 367). Tags `[ZTDId]`, `[OrderID]:x`, `[PurchaseOrderID]:x` in `devicePhysicalIds` drive dynamic-group assignment (PDF pp. 338, 368).
4. **Autopilot self-deploying mode proves device identity with TPM 2.0 attestation — no user credential at all.** "The TPM identifying information is embedded inside" the hardware ID; a TPM attestation handshake gates the credential-less AAD join. It deliberately fails on VMs (even with vTPM), and real-world TPM quirks abound: TPM 1.2 won't work, some 2.0 chips have attestation disabled or need flash upgrades — failures surface ~95% through provisioning (PDF pp. 364–365, 371). White Glove pre-provisioning has the same TPM-attestation + physical-hardware + wired-Ethernet requirements (PDF pp. 390–392).
5. **Enrollment restrictions are a first-class control plane.** Intune device-type restrictions can *block personally-owned devices* outright; "corporate-owned" is defined by enrollment path (device-enrollment-manager account, Autopilot, bulk AAD token via `.ppkg`, or SCCM co-management). Azure AD device settings separately gate *which users may join devices*, per-user device count (default 50 → recommend 1–2), and who becomes local admin (PDF pp. 70–71, 348).
6. **Bulk enrollment = time-boxed bearer token baked into a provisioning package.** WCD `.ppkg` "Enroll in Azure AD" uses a bulk AAD token with an explicit expiry date; it *cannot be revoked* once baked — the workaround is deleting the token's corresponding AAD account (PDF p. 321). `.ppkg` can be applied at OOBE (auto via USB, or Win-key ×5 mid-OOBE) or post-install by a local admin; it is a *one-time* provisioning action, explicitly not ongoing management (PDF pp. 324–326).
7. **GPO-bootstrapped auto-enrollment is a scheduled-task mechanism, not magic.** The "Auto MDM Enrollment with AAD Token" GPO creates a Task Scheduler entry (`EnterpriseMgmt` → `deviceenroller.exe`) that retries **every 5 minutes for 1 day** then self-destructs; `dsregcmd /status` exposes `MdmUrl`/`AzureAdJoined` state for debugging (PDF pp. 156–160).

### Policy / compliance model

8. **Policy sync is device-pull with a fast-then-slow cadence.** Windows PCs check in every 3 min for the first 30 min after enrollment, then ~every 8 h (steady state "typically about every six hours"); the service can nudge but "it is still up to the device to check in" (PDF p. 184). Manual sync exists via Settings → "Access work or school" → Sync or Company Portal "Check access" (PDF pp. 119, 480–481).
9. **Per-setting status taxonomy: Conforms / Not Applicable / Pending, plus a Conflict column.** "Not Applicable" devices count as compliant (you can't flag an iOS98 device for missing an iOS99-only setting) — capability absence ≠ noncompliance (PDF pp. 184–185, 425–426). Intune baseline monitoring additionally reports per-setting *Conflicts* between profiles (PDF p. 436).
10. **CSP policy removal reverts the setting — policies are not tattoos.** Deleting the profile assignment + resync reverts e.g. `AllowCortana` 0→1 under `HKLM\Software\Microsoft\PolicyManager\current\device` (PDF pp. 119–120). Settings have a declared **User vs. Device scope** that the admin must respect; nothing warns you if you target wrongly (PDF pp. 117–118).
11. **MDM-vs-GroupPolicy conflict resolution is non-deterministic by default.** Without `ControlPolicyConflict/MdmWinsOverGP=1` (custom OMA-URI `./Vendor/MSFT/Policy/Config/ControlPolicyConflict/MdmWinsOverGp`), last/first-writer behavior is inconsistent; with it, MDM wins — but in 1803 it was a *one-way, non-deletable* setting (PDF pp. 161–166). The endpoint logs the decision: `DeviceManagement-Enterprise-Diagnostics-Provider` event ID **2220** reports the `MdmWinsOverGp` value (PDF p. 161).
12. **Compliance posture has a fail-closed default option.** "Mark devices with no compliance policy assigned as → Not Compliant" is recommended over the lenient default, to catch an admin silently stripping all policies (PDF p. 419). Actions for noncompliance are graduated: mark noncompliant → templated email to the end user (~10–15 min) → (mobile-only) remote lock — **"remotely lock the noncompliant device" is explicitly NOT supported on Windows 10 desktop** (PDF p. 422).
13. **Health attestation only re-evaluates at reboot + sync.** BitLocker-compliance attestation won't flip noncompliant→compliant until the machine reboots and resyncs; compliance reporting latency can reach ~10 h (PDF pp. 424–426). The attestation signal chain is SGRA (System Guard Runtime Attestation) → optional Defender ATP risk signal → Intune compliance verdict → Azure AD Conditional Access grant ("Require device to be marked as compliant") → optional session controls ("limited access experience," e.g., no OWA attachments) (PDF pp. 460–465, 468, 470).
14. **Zombie device records need explicit GC.** Intune "device cleanup rules" auto-delete devices that haven't checked in for a configurable 90–270 days (PDF p. 426).

### Device actions & lost/stolen handling

15. **Device actions are a *tiered destructiveness ladder* with explicit enrollment-preservation semantics** (Table 8.1, PDF p. 362): Retire (unenroll; policies removed, some stick; personal data kept — PDF p. 361) → Fresh Start/Clean PC (strip Win32/UWP apps, upgrade Windows, optionally keep user data — PDF p. 362) → Wipe / Wipe-retain (full factory reset ± keep enrollment; **"Wipe protected" = "same as wipe, but with protections to prevent it from being stopped"**) → Autopilot Reset (wipe apps/data/settings but **preserve AAD join, MDM enrollment, language, Wi-Fi profiles** — the machine re-provisions itself with no OOBE).
16. **Autopilot Reset is self-healing re-provisioning, and the local variant is policy-gated.** Local reset = `Win+Ctrl+R` at the logon screen + admin creds, only if `PolicyCSP/CredentialProviders/DisableAutomaticReDeploymentCredentials` was pushed first; remote reset warns the user "will restart in 45 minutes" then re-enrolls itself (PDF pp. 358–361).
17. **Remote lock on desktop Windows barely exists in stock MDM.** Remote lock/reset via Company Portal is documented for *phones*; the Windows-desktop lost-device story is BitLocker (data-at-rest) + Wipe (destructive) + Retire — there is no "lock the OS but keep it intact and recoverable" primitive. The theft narrative in the book is literally "nuke it from the sky" (PDF pp. 358, 479–481).
18. **Remote unenrollment is deliberately dangerous as an anti-orphan safeguard.** "When devices are remotely unenrolled from MDM, the AAD association is also removed… to avoid leaving the corporate devices in an unmanaged state" — may force re-image (PDF p. 185).

### Windows security stack & updates

19. **BitLocker escrow can be made a *precondition* of encryption.** Endpoint-protection profile: "Encrypt devices = Required" + "Allow standard users to enable encryption during Azure AD Join" (works post-join, despite the name) + "Save BitLocker recovery information to AAD" + "**Store recovery information in AAD before enabling BitLocker**" = no encryption until keys are provably escrowed (PDF pp. 439–441).
20. **Key-recovery access is role-scoped and self-serviceable.** The *device owner* (first person to enroll) can read their own recovery keys at `myapps.microsoft.com`; admin roles that can read keys: Global Admin, Helpdesk Admin, Security Admin/Reader, Intune Service Admin, Cloud Device Admin; bulk export via PowerShell/Graph for off-Azure backup. Standard users *cannot* back up keys locally (UAC) without elevation tooling (PDF pp. 442–448).
21. **AppLocker via MDM both weakens and widens reach vs. Group Policy.** Deployed as raw exported AppLocker XML through a custom OMA-URI (trimmed to the rule-collection subtree) — clumsy, but it works on **Windows 10 Pro**, whereas GP AppLocker requires Enterprise/Education (PDF pp. 451–456, esp. p. 417 overview line 8603).
22. **Update management = rings + deferrals + delivery optimization, not version pinning.** Ring properties: servicing channel (SAC / Insider), deferral days for quality vs. feature updates, Active Hours, feature-update uninstall window (rollback days); assigned to groups like any profile (PDF pp. 404–406). Delivery Optimization does peer caching of update content (PDF pp. 400–401); `Update/UpdateNotificationLevel` suppresses user-facing update nags for kiosk/self-deploy devices (PDF pp. 366–367).
23. **Observability stack is layered:** per-profile delivery reports (device/user status) → on-device "MDM Advanced Diagnostic Report" (GPResult equivalent: Managed / Blocked-by-GP / Unmanaged policy sections) → `DeviceManagement-Enterprise-Diagnostics-Provider` Admin+Operational+Debug event channels (deployment errors are event IDs 1900–1930) → remote diagnostic-log collection via OMA-URI on 1903+ (PDF pp. 174–183, 233).
24. **Enrollment Status Page (ESP) can block device use until required state converges** — "Block device use until these required apps are installed" plus "Allow users to use device if installation error occurs" toggle (PDF p. 344).

## What MDM does that we don't — and what our pre-boot layer adds that MDM cannot

**Gaps they have that we lack** (candidate deltas): enrollment restriction plane (platform allow/deny, block-personally-owned, per-user device quota, DEM accounts); bulk/time-boxed enrollment tokens; a tiered action ladder with a *non-stoppable* wipe variant and an *enrollment-preserving* reset; a separate compliance state machine feeding graduated responses (warn→limit→block) instead of our binary lock verdict; per-setting status + conflict reporting; remote diagnostic-bundle collection; staged update rings; a user-facing self-service portal (own keys, own-device reset); automatic GC of dead device records; role-scoped recovery-key reads.

**What we add that OMA-DM/CSP-class MDM structurally cannot do** (the book itself is the proof: every mechanism above executes inside a live, enrolled, online Windows — a thief who reinstalls the OS, swaps the disk, never boots Windows, or keeps the machine offline escapes all of it): PBL's UEFI pre-boot gate (`Decision.c`) locks *before* any OS loads; `ChainLoad.c`/`Bcd.c` gate the boot path itself; TPM-sealed monotonic policy counters survive OS reinstall; the deadman switch converts *silence* into lockdown (the opposite of Intune's cleanup-rules GC); override challenge/response works with no OS at all. Even Intune's strongest lost-device story is "BitLocker (data-at-rest) + Wipe (destructive) + Retire" — there is no non-destructive, reversible, pre-OS remote lock; that is our core differentiator. Also notable: their BitLocker compliance signal only refreshes at reboot+sync — exactly the window where our boot-time verdict is already enforced.

## New capabilities this suggests (concrete)

1. **Attested enrollment (self-deploy analog):** bind `POST /v1/enroll` to a TPM `TPM2_Quote`/EK-cert proof at enrollment time instead of deferring attestation to `/v1/attest`; reject enrollment from platforms that can't attest (book's hard-won lesson: vTPM/VMs deliberately fail, attestation-capable TPM 2.0 is a real hardware gate — PDF pp. 364–365, 371).
2. **Enrollment hardening plane:** device-type/serial allowlist, per-operator device quota, "block personally-owned" flag keyed on enrollment path (bulk token / PBL-attested / manual) — mirrors Intune enrollment restrictions; closes the open-POST gap on `/v1/enroll` (PDF pp. 70–71).
3. **Time-boxed bulk enrollment tokens:** installer embeds a revocable, expiring enrollment credential (analog: `.ppkg` bulk AAD token + expiry — PDF p. 321); server tracks token→device rows so revocation = delete token record.
4. **Escrow-verified-before-arm gate:** adopt "store recovery information before enabling" — server withholds final `locked` verdict until the agent's RSA-wrapped recovery key lands (currently key material rides the *post-lock* pending-ACK; consider pre-arm escrow for the E-ENCRYPT path) (PDF pp. 440–441).
5. **Command lifecycle states we lack:** add `not_applicable` and `conflict` result statuses (agent reports "command inapplicable to this platform/config" instead of silent success/failure), and a per-command detail field — mirrors Conforms/Not-Applicable/Pending/Conflict (PDF pp. 184–185, 436).
6. **Tiered action ladder:** distinct `retire` (unenroll, release policy), `wipe` (destructive, credential-wipe), and `reset-preserve-enrollment` commands; consider a `wipe_protected` flag that the agent cannot abort once acknowledged — the book's "Wipe protected" (PDF pp. 361–362).
7. **Compliance-policy-as-code:** a policy-evaluated `compliant/noncompliant` state distinct from the lock verdict, driving graduated responses (notify → restrict → lock) rather than binary; plus a **fail-closed default**: "devices with no policy assigned → noncompliant" (PDF pp. 419, 422).
8. **Noncompliance notification ladder:** templated email/webhook to the device owner on noncompliance before lock (Intune: mark → email → act; we jump straight to lock) (PDF p. 422); hook into `server/src/notifications/`.
9. **Role-scoped recovery-key reads:** split `pba-credentials` from blanket `super-admin` into a dedicated "key-reader" role + per-access audit row (Intune delegates to Helpdesk/Security-Reader roles; PDF pp. 447–448).
10. **Agent update rings:** pilot/broad channels + deferral days + rollback window for `E-AUTO-UPDATE` (`/api/agent/update` currently single-channel) (PDF pp. 404–406).
11. **Remote diagnostic-bundle command:** agent collects and uploads a diagnostic report on demand (their 1903+ OMA-URI log collection; PDF p. 183) — we have `agent_diagnostic.py` locally but no server-triggered fetch.
12. **Applied-policy report:** expose "what policy version/settings actually took effect on this agent" in the dashboard — their Advanced MDM Diagnostic Report equivalent (GPResult-for-MDM; PDF pp. 175–177).
13. **Device-record GC policy:** configurable auto-retire of devices silent > N days — but note our deliberate inversion: silence → deadman *lock*, not deletion; GC should apply to *released/retired* records only (PDF p. 426).
14. **User self-service surface:** owner-portal for own-device recovery-key display + own-device "reset/track" requests pending operator approval (Company Portal + `myapps.microsoft.com` key self-service; PDF pp. 446, 479–481) — pairs with existing `duress.py`/PBA credential machinery.
15. **Reboot-gated attestation awareness:** their BitLocker-attestation-needs-reboot lag (PDF p. 424) validates our design — note in docs that PBL's boot-time platform-state digest is evaluated at *every* boot with no sync lag; document as a competitive advantage.

## Glossary (MDM-domain terms, delta from STUDY-INDEX glossary)

- **OMA-DM** — Open Mobile Alliance Device Management; XML protocol for enrollment + command push; Windows 10's in-box MDM engine speaks it (PDF p. 43).
- **CSP** — Configuration Service Provider; per-feature in-OS receiver of OMA-DM directives (e.g., Policy CSP, BitLocker CSP, AppLocker CSP) (PDF pp. 43–45).
- **WMI-to-CSP bridge** — in-box way to drive CSPs from scripts/WMI with no MDM service at all (PDF p. 45).
- **First/third-class settings** — CSP settings surfaced in the MDM GUI vs. reachable only by hand-built custom OMA-URI (PDF pp. 46, 121–124).
- **Workplace Join vs. MDM enrollment** — AAD-registered (SSO only) vs. AAD-joined+enrolled (managed); the classic two-step trap (PDF pp. 74–76).
- **Hardware hash / hardware ID** — ~4 KB Autopilot device fingerprint (serial + product ID + TPM-identifying data) pre-registered to a tenant (PDF pp. 328–334).
- **DEM** — Device Enrollment Manager account; marks devices corporate-owned (PDF p. 71).
- **`.ppkg` / WCD** — Windows Configuration Designer provisioning package; carries bulk AAD token, certs, apps; one-time action (PDF pp. 315–326).
- **ESP** — Enrollment Status Page; blocks device use until assigned apps/policies converge (PDF p. 344).
- **SGRA** — System Guard Runtime Attestation; Windows health-attestation signal feeding compliance→conditional access (PDF pp. 460–461).
- **Retire / Wipe / Autopilot Reset / Fresh Start** — the Intune destructiveness ladder; reset preserves enrollment, wipe optionally does, retire only unenrolls (PDF pp. 358–362).
- **MdmWinsOverGP** — `PolicyCSP/ControlPolicyConflict` setting making MDM deterministic-winner over Group Policy (PDF pp. 161–166).
- **Update ring** — servicing channel + quality/feature deferral days + active hours + uninstall window, group-assigned (PDF pp. 404–406).
