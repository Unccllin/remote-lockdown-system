# Beyond BIOS (3rd Edition) — Delta Study Note

## Source

- **Title:** Beyond BIOS: Developing with the Unified Extensible Firmware Interface, **Third Edition**
- **Authors:** Vincent Zimmer, Suresh Marisetty, Michael Rothman (Intel Press / Walter de Gruyter, © 2017)
- **Source type:** Book PDF — `docs/reference/books/beyond-bios.pdf` (325 PDF pages)
- **Spec baseline:** UEFI 2.6 / PI 1.5 era (UDK2015). Predates UEFI 2.10, SBAT, FMP-as-shipped, HTTP-boot hardening details — treat as architecture/mechanism guidance, not current spec text.
- **Page citation convention:** Book page numbers are cited as `p.N`; PDF page = book page + 19 (e.g., book p.127 = PDF p.146). Front matter is PDF pp.1–19.
- **Companion notes this deltas against:** `STUDY-UEFI-SPEC-2.10.md` (spec text, Secure Boot databases, image services), `STUDY-EDK2.md` (DxeCore, BdsDxe, DxeImageVerificationLib, build system), `STUDY-INTEL-PLATFORM-SECURITY.md` (SPI/SMM/DMA hardware details).
- **Coverage caveat:** This book is an architecture/design-rationale text, not a spec. It is thin on SMM internals, authenticated-variable wire formats, and DxeImageVerificationLib detail — those are better covered by the other notes. Its unique value is **boot-manager policy semantics, connect/dispatch ordering, vendor-variability rationale, and deployment/update plumbing** that the spec text does not spell out.

## One-paragraph technical overview

Beyond BIOS explains *why* the PI/UEFI phases and protocols are shaped the way they are, from the architects who designed them. The delta-relevant material is concentrated in five areas: (1) the firmware boot manager's exact policy contract — `Driver####` before `Boot####`, `BootNext` deletion, watchdog arming, `EFI_SUCCESS`-vs-failure return semantics, and the BDS↔DXE-dispatcher handshake that re-runs dispatch when connect fails; (2) the connect model — driver-model DXE drivers do *not* touch hardware until BDS calls `ConnectController()`, and optimized platforms may connect only the devices on the boot target's path, which directly determines whether PBL's NIC, console, and ESP are usable when `PblAppEntryPoint` runs; (3) boot-path diversity — S3 resume bypasses DXE/BDS entirely via the OS resume vector, and recovery/flash-update boot modes supersede normal boot, meaning there are reboots where PBL never executes; (4) console/HII realities — the console splitter, `ConOut` multi-instance device paths, guaranteed-basic-Latin-only text output, and no font/image guarantee on headless platforms; and (5) update plumbing — `UpdateCapsule`/`EFI_CAPSULE_BLOCK_DESCRIPTOR` scatter-gather, `BOOT_ON_FLASH_UPDATE`, ESRT+FMP capsule routing, and the CRTM-only-validation rule for root-of-trust updates.

## Key technical facts/mechanisms (delta only)

### BDS / boot-manager policy

1. **A `Boot####` returning `EFI_SUCCESS` stops boot processing and shows a boot menu; a non-success return advances to the next `BootOrder` entry** (p.186). This is the inverse of the usual intuition. For PBL: if `ChainLoadBootManager` fails and `PblAppEntryPoint` returns `EFI_SUCCESS`, the platform *stops* and presents a menu — it does not fall through to a (potentially unsafe) next boot option. Conversely, returning an error on BLOCK causes the boot manager to try the **next** `Boot####`, which may be an unprotected fallback path. PBL's BLOCK path should therefore either reset the platform or keep control (lock screen → `ResetSystem`), never return an error that advances `BootOrder`. → `PblApp.c`, `Decision.c`, `LockScreen.c`, `ChainLoad.c`.

2. **The boot manager arms a 5-minute watchdog (`SetWatchdogTimer`) before every `StartImage()` and disarms it only if the image returns** (p.186). If no handler is registered on the Watchdog Timer Architectural Protocol, expiry calls `ResetSystem()` (p.138). PBL inherits this watchdog: a hung HTTPS fetch or TPM command will reset the machine after ~5 min — a fail-safe *for* lockdown (a wedged PBL reboots rather than soft-bricks), but also a bound on verdict-fetch latency budgets. PBL can call `gBS->SetWatchdogTimer()` itself to extend or disable it. → `PblApp.c`, `HttpsClient.c`, `TpmClient.c` timeouts.

3. **`Driver####`/`DriverOrder` are always processed before `Boot####`/`BootOrder`; `BootNext` is tried first and deleted before transfer** (p.186, 190). `Driver####` entries marked `LOAD_OPTION_FORCE_RECONNECT` (0x2) cause *all* drivers to be disconnected and reconnected after the last `Driver####` runs (p.188). A hostile or misconfigured `Driver####` can therefore re-shuffle the driver stack immediately before PBL is loaded. `PlatformState.c` should treat the `DriverOrder` list and `BootCurrent` (which records which `Boot####` launched PBL, p.190) as platform-state inputs. → `PlatformState.c`, `Decision.c`.

4. **BDS is *required* to re-invoke the DXE dispatcher when a console connect, driver load, or boot attempt fails**, because connect attempts can surface new firmware volumes (e.g., on a hot-plugged or newly-enumerated device) containing the needed drivers (p.127–128, 124). A `Boot####` that initially fails may be retried after re-dispatch. Implication: transient "device not found" at PBL launch can self-heal; conversely PBL should retry `LocateHandle`/`ConnectController`-backed lookups before declaring a missing TPM/NIC. → `HttpsClient.c`, `TpmClient.c`, `PlatformState.c`.

5. **Driver-model DXE drivers do no hardware init at dispatch time — they only register Driver Binding protocols; BDS `ConnectController()` is what actually starts devices** (p.127, 38). Optimized platforms deliberately skip `BdsConnectAll()` and connect *only* the devices on the boot target's device path (p.248–249). **On fast-boot/S3-optimized firmware, the NIC may not be connected when PBL runs** — `EFI_HTTP_PROTOCOL` may exist (driver dispatched) while no `ConnectController` has bound the SNP/UNDI stack to the adapter. PBL should either (a) call `gBS->ConnectController()` on the network controller handle from its own device path before fetching, or (b) document that its `Boot####` device path must traverse the network device so BDS connects it. This is a top reliability item for real-hardware bring-up (D-129). → `HttpsClient.c`, `PblApp.c`, deployment docs.

6. **S3 resume does not run DXE/BDS at all** — the PEI S3 path restores memory via the **Hardware Save Table** (a script of predefined I/O/memory write records saved during the G0→S0 path, stored in firmware-reserved/E820-type-4 memory) and jumps straight to the OS resume vector (p.197, 200–201, 248 Fig 15.5). **PBL never executes on S3 resume.** This is architecturally expected (Windows resume doesn't re-run bootmgfw), but it means: (a) MOR/spi-lock state on resume depends entirely on the save-table replay — matching the known S3-boot-script attack surface where `FLOCKDN`/`BLE` are re-programmed by a replayed script; (b) lock enforcement cannot rely on PBL running at resume; sealed-PCR BitLocker is the only enforcement on the S3 path. → `Mor.c`, `SpiProtections.c`, `Decision.c` (document the gap).

7. **Boot modes are a PI-level enum with priority ordering** — `BOOT_IN_RECOVERY_MODE` (0x20) > `BOOT_ON_FLASH_UPDATE` (0x12) > `BOOT_ON_S3_RESUME` (0x11) > minimal/full/diagnostic/default-config variants (p.196–197, 205–206). A capsule-update or recovery reboot *supersedes* an S3 resume cause. In recovery mode the PEI dispatcher restarts itself dispatching only recovery PEIMs, then typically hands to DXE for peripheral access (p.201–203). On `BOOT_ON_FLASH_UPDATE`/recovery boots PBL's `Boot####` may not be processed at all — firmware update and recovery flows bypass normal boot policy, which is both an expected gap and a channel the update mechanism (below) uses. → deployment/runbook docs.

8. **The boot manager may garbage-collect load options** — remove unparseable `Boot####`, prune `BootOrder` entries with no backing variable, and reorder its own options (p.186). If PBL's `Boot####` file path is unresolvable on a given boot (e.g., ESP on a disk that enumerates late), some firmwares may *delete or demote* the entry rather than retry. Deployment should verify the entry survives across boots on target hardware; a defensively-installed second entry or fallback `\EFI\BOOT\BOOTX64.EFI` placement may be warranted. → installer/`deploy` scripts, D-129.

9. **Short-form device paths (starting at an HD media node) are matched by partition GUID/MBR signature + partition number; if more than one device matches, the boot manager picks arbitrarily** (p.187). Two disks with cloned ESPs make PBL's launch source nondeterministic — relevant both to reliability and to an attacker planting a matching-signature disk. PBL should record its actual `LoadedImage->DeviceHandle`/`FilePath` into the platform-state digest so the attestation shows which ESP served it. → `PlatformState.c`, `ChainLoad.c`.

10. **Default-boot fallback (no valid `BootOrder`) enumerates removable media first, then fixed media, booting `\EFI\BOOT\BOOT{ARCH}.EFI`** (`BOOTX64.EFI` for x64, PE machine type 0x8664, p.191–192). These auto-created options are not persisted. PBL deployed as the removable-media fallback name gets launched even with wiped NVRAM — a viable recovery/first-provisioning channel — but the same path is how attacker media boots, so `Decision.c` must not treat "launched via fallback" as trustworthy. → `Decision.c`, installer docs.

### Console / HII / user interaction

11. **`ConOut`/`ConIn`/`ErrOut` are multi-instance device paths and the *console splitter* owns the System Table slots** — output is fanned to every active console (local screen, serial, terminal, even HTTP remote console) and input merged from all of them (p.82, 92–94). Two consequences: (a) `LockScreen.c` text may also go out a serial/network console — don't print anything sensitive in lock output; (b) `ReadKeyStroke` input can arrive from a remote console, so the override challenge can be answered over a remote pipe — acceptable (it's challenge/response) but worth documenting. `ConIn/ConOut/ErrOut` are always subsets of `ConInDev/ConOutDev/ErrOutDev`; firmware may auto-repair unresolvable console paths (p.189–190). → `LockScreen.c`, `Override.c`.

12. **Simple Text Output is only required to support the basic-Latin Unicode subset**, and HII font/image repositories are *not* guaranteed — headless platforms may have no local rendering at all (p.81, 152). `LockScreen.c` must render the lock UI in ASCII-only, handle `gST->ConOut == NULL` (already does, but now justified), and not depend on HII images/fonts. → `LockScreen.c`.

13. **A hot-plugged input device is not usable until its bus driver calls `ConnectController()`** — USB keyboard insertion mid-boot only becomes an input console if the USB bus driver performs the connect on hot-add (p.38–39). On platforms where the bus driver doesn't, a user at the lock screen may have a dead keyboard. `LockScreen.c`/`Override.c` should tolerate "no ConIn ever signals" (timeout → remain locked, don't hang forever against the armed watchdog). → `LockScreen.c`, `Override.c`, D-129.

14. **HII configuration is programmatically accessible**: drivers register IFR forms + strings via `NewPackageList()` against their device handle; the `x-UEFI-ns` keyword namespace lets an agent locate a named setting by matching Prompt Tokens to strings, and `EFI_HII_CONFIG_ROUTING_PROTOCOL.ExtractConfig()/RouteConfig()` get/set values without a UI (p.152–156, 288–292). PBL could read firmware setup state (e.g., "is Setup-lock enabled", chassis-intrusion, manufacturing mode) via HII keywords instead of fragile vendor variables — worth prototyping on real hardware. → `PlatformState.c` (new capability).

### Variables, counters, capsule update

15. **Variable attribute changes are not honored on rewrite — you must delete (SetVariable with 0-size data) and recreate with new attributes**; attributes apply only at creation; every variable needs ≥1 byte; volatile variables are the sanctioned "mailbox" between components that must not touch NVRAM (p.76–77). Post-`ExitBootServices`, only `NV|RT` variables are writable and `RT`-only (volatile RT) variables become read-only (p.77). PBL's own variables (counters, cached verdict, lock marker) are created `NV|BS|RT` at first boot — any later attribute tightening requires delete+recreate logic in the installer, not an in-place write. → `Override.c`, cached-verdict code, installer.

16. **The platform monotonic counter is split**: low 32 bits are volatile, reset each boot, incremented per `GetNextMonotonicCount()` call (boot-services only); high 32 bits are nonvolatile, bumped on reset/overflow via `GetNextHighMonotonicCount()` (runtime only) (p.79). This is a **firmware-provided anti-rollback counter** usable now: PBL can bind cached verdicts to `(high32, boot-low32)` or store `high32` in TPM NV and reject verdicts/policy older than the last-seen high count — a hardware freshness anchor independent of wall-clock time (RTC can be rolled back). → `Verdict.c`, `Override.c`, `Policy.c` (new capability, complements D-118 RNG).

17. **`UpdateCapsule` takes a scatter list**: `EFI_CAPSULE_BLOCK_DESCRIPTOR` carries both virtual and physical address ranges so an OS can describe discontiguous physical pages; `QueryCapsuleCapabilities` returns whether a capsule type is supported and which `ResetSystem()` reset type will process it across the reset (p.79–80). Capsule processing then runs on a `BOOT_ON_FLASH_UPDATE` boot before normal boot policy (fact 7). For PBL: `PblApp.efi` lives on the ESP so capsule update doesn't directly apply, but the *same* machinery is the right mental model for a signed `pbl-update.cap` flow if PBL ever needs firmware-mediated self-update; near-term, signed-ESP-file update (sbsign'd image + `Boot####` repoint) is the practical E-AUTO-UPDATE analog. → `sign-efi.sh`, D-130, E-AUTO-UPDATE docs.

18. **CRTM updates must be validated using only CRTM code and data** — nothing outside the root may be trusted until verified; the signed capsule is staged and validated at the *next reset* by the CRTM itself (p.168–169). The embedded-platform variant uses a strap-pin/boot-block write-protected region as the hardware RoT (p.265). This confirms the deployment invariant: PBL can never "update the root"; it can only update itself within the policy the root (PK/KEK/db) permits — i.e., PblApp.efi must be signed by a `db`-anchored cert, and `pbl-test-signing` certs must be enrolled into `db` (test) or replaced by the production chain. → `sign-efi.sh`, D-130, `CODE-SIGNING-GUIDE.md`.

19. **ESRT + FMP is the sanctioned in-band firmware-update topology**: the EFI System Resource Table exposes updatable elements (GUID+version) to the OS, an update capsule carries a routing hint, and each device's Firmware Management Protocol performs the update — all distinct from `UpdateCapsule` for system firmware (p.48–49). If a future PBL wants the *server* to drive firmware-level remediation (e.g., push a BIOS update to a device failing attestation), ESRT enumeration is the discovery mechanism and FMP the apply path. → server/verdict design docs (new capability).

### Security/trust model

20. **The book draws the trust boundary as PM_AUTH = {SEC, PEI core, PEIMs, DXE core/drivers, FVs, PEI/DXE-private variables, BDS, SMM, UEFI runtime, ACPI/SMBIOS tables}**; non-PM_AUTH = unsigned HBA drivers and unsigned OS loaders from the ESP (p.178–180). PBL sits exactly at the boundary: it is a third-party ESP executable (non-PM_AUTH) that the platform will run only because Secure Boot admits it. This framing should anchor `Decision.c` comments: everything PBL reads (variables, BCD, ESP files) is *outside* the manufacturer-controlled set and therefore attacker-modifiable unless authenticated (signed policy/verdict) or measured (PCR 13 digest). → `Decision.c`, `PlatformState.c`, `PolicyRootOfTrust.c`.

21. **PEI-phase authentication is a two-PPI design**: a Verification PPI checks a PEIM (signature/checksum/OEM scheme) and a Security PPI decides defer-vs-execute and may emit an attestation log entry (p.219); the DXE analog is that every dispatched DXE driver is authenticated by the Security Architectural Protocol before execution (p.124). This is the same defer/log pattern PBL uses (evaluate → extend PCR 12/13 → allow/lock), confirming PCR-extension-before-enforcement is the architecturally intended order. → `PblApp.c` ordering comments, `TcgLog.c`.

22. **Driver selection precedence under `ConnectController()` is: Platform Driver Override > Bus Specific Driver Override (e.g., a PCI option-ROM driver) > general `Driver####`/search** (p.36–38). A NIC/storage card's own OpROM UEFI driver can *preempt* the platform's `Driver####` driver — so the network stack PBL gets may come from an adapter ROM, not the BIOS vendor's build. For attestation this means `LoadedImageCount`/driver provenance varies per machine; for security, OpROM drivers are non-PM_AUTH code running before PBL. → `PlatformState.c` (loaded-image inventory), D-129 quirks list.

23. **The TCG/TPM protocol is intended to be installed at the *start* of DXE** so that DXE and UEFI images themselves get measured before the OS loader continues the chain (p.166–167); the book's measured-boot PCR example: PCR0 firmware, PCR1 ACPI/E820/EFI tables, PCR2 option ROMs, PCR4 OS IPL, PCR8 kernel (p.266). Consistent with `TpmClient.c`'s assumption that `EFI_TCG2_PROTOCOL` exists by the time a `Boot####` app runs — but worth a defensive `LocateProtocol` retry (fact 4) since TCG-dxe dispatch order is vendor-controlled. The S-CRTM also owns physical-presence detection per the TCG privacy model (p.163–164) — PBL cannot reliably assert physical presence itself; override UX should not claim it does. → `TpmClient.c`, `Override.c`.

24. **UEFI error records are a firmware-mediated NVM store readable by the OS** (WHEA on Windows): records keyed by notification-type/creator-ID GUIDs, persisted to platform NVRAM via variable services, for CMC/MCE/NMI/PCIe/boot errors (p.274–280). **New capability:** PBL could write lockdown/tamper events as UEFI error records with a PBL creator GUID, giving the post-boot agent a standardized, OS-visible channel for "why did PBL block" that survives even when `bootmgfw` was never started — cleaner than bespoke variables. → `LockScreen.c`/`Decision.c` logging (new capability), agent-side reader.

25. **Driver Health Protocol (`GetHealthStatus`/`Repair`) and UEFI User Identification (credential-provider drivers, multi-factor user policy) are pre-boot facilities PBL can consume** (p.48, 176–177). Driver Health is a graceful path for a sick boot device; UID could give `Override.c` a standards-based local-auth factor (smartcard/biometric) instead of only challenge/response. → `Override.c`, `Decision.c` (new capabilities).

### Networking in pre-boot

26. **The TLS/HTTP stack layering is `HttpDxe`/`TlsDxe` over `TcpDxe`**, with `EFI_TLS_PROTOCOL` + `EFI_TLS_CONFIGURATION_PROTOCOL` produced per connection and usable for non-HTTP purposes too (p.175–176). HTTP boot proper adds DNS resolution and a DHCPv6 boot-file URL option (RFC 5970) over routable port 80/443, plus EAP-TLS supplicant support for Wi-Fi UNDI (p.51, 174–176). Practically: on platforms supporting HTTPS boot the same TLS plumbing PBL uses is exercised by the firmware itself; on platforms with only IPv4/no-DNS pre-boot, PBL needs a literal-IP or pre-resolved verdict endpoint. `IPsec`/`iSCSI` pre-boot stacks exist but are out of PBL's scope. → `HttpsClient.c`, `TlsVerify.c` (endpoint-config requirements), deployment docs.

27. **TPL discipline**: notification functions run at their registered TPL; `TPL_HIGH_LEVEL` masks even the single timer interrupt, so event callbacks must be short; timer-based events (e.g., a verdict-fetch timeout, watchdog) can't fire while a notification holds TPL_HIGH (p.28–29). PBL's event-driven input/timeout code in `LockScreen.c`/`HttpsClient.c` must not run long work inside `TPL_NOTIFY`+ callbacks. → `LockScreen.c`, `HttpsClient.c`.

## New capabilities this suggests

1. **Monotonic-counter freshness for verdicts** (fact 16): bind `GetNextHighMonotonicCount()` into the verdict/C4 policy freshness check — a rollback-resistant ordering anchor that doesn't trust the RTC.
2. **UEFI error-record lock logging** (fact 24): write `PBL_LOCK` records (creator GUID = PBL) to the platform error store so the Windows agent/WHEA can read *why* a machine is locked without bespoke NVRAM parsing.
3. **HII keyword probing** (fact 14): `ExtractConfig`/`RouteConfig` + `x-UEFI-ns` gives a semi-standard way to read BIOS setup knobs (chassis intrusion, manufacturing mode, setup password presence) into the platform-state digest — higher-fidelity than guessing vendor variables.
4. **Fallback-name deployment mode** (fact 10): installing PBL as `\EFI\BOOT\BOOTX64.EFI` gives a zero-NVRAM provisioning path for recovery/first-boot scenarios, gated by policy that treats fallback launch as untrusted.
5. **`ConnectController` self-healing** (facts 4–5): make `HttpsClient.c` connect its own NIC (walk `PciIo`/SNP handles, `ConnectController`) so verdict fetch works on fast-boot firmware that never ran `BdsConnectAll`.
6. **UID-based local override** (fact 25): UEFI User Identification could replace/augment the challenge-response override with a standards-based credential provider on enterprise hardware.
7. **ESRT/FMP-driven firmware remediation** (fact 19): a server verdict of "firmware too old / vulnerable" could eventually trigger a capsule-based firmware update rather than just a block — aligns E-AUTO-UPDATE's ambition with the sanctioned update plumbing.
