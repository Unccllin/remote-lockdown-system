# Deploying Remote Lockdown to a company's Windows fleet

**Audience**: whoever installs this at a client site, and whoever answers the client's IT questions.
**Scope**: the Windows admin console and the Windows agent. Firmware (PBL) is **not** covered here — it
is not deployable to clients yet (see `docs/adr/PBL-DEBT-LEDGER.md` D-129/D-130/D-134).

---

## 1. Why this document exists: the three different "Windows blocked it" dialogs

They look alike and the remedies are different. Reading the dialog wrong sends people to the wrong fix.

| What the user sees | What it is | What actually resolves it |
|---|---|---|
| *"Windows protected your PC"* → **More info → Run anyway** works | SmartScreen **reputation**: the file is new and has not been seen enough | Avoid the **Mark of the Web** (§2), or earn reputation over time (§4) |
| *"setup.exe isn't commonly downloaded"* in Edge | same reputation check in the browser | same |
| **No "Run anyway" at all** — only "Get apps from the Store" | **Smart App Control** (Windows 11) | signed by a certificate in Microsoft's Trusted Root Program, or recognised by Microsoft. **There is no per-app exception** |

A downloadable consumer installer will always hit the first row. **A company deployment does not have
to**, because the trigger is the Mark of the Web — the "this came from the internet" tag Windows adds to
browser and email downloads — and managed deployment never sets it.

Two consequences worth stating plainly to a client:

- Installing through Intune/GPO/network share is not a trick to dodge a security check; it is the normal
  way software reaches a managed fleet, and it is the only channel where the reputation prompt does not
  exist.
- **Never** advise a client to disable SmartScreen or to "just click Run anyway". We are asking them to
  trust a lockdown agent; asking them to weaken a control at the same time is a lost argument.

## 2. The recommended channel: deploy, don't download

### 2a. Intune — Win32 app wrapping the NSIS installer

1. Download `remote-lockdown-admin-<version>.exe` from the GitHub release **on the admin workstation**,
   not on the target.
2. Wrap it with the Microsoft Win32 Content Prep Tool (`IntuneWinAppUtil.exe`) and upload as a Win32 app.
3. Install command: `remote-lockdown-admin-<version>.exe /S` (NSIS silent switch).
4. Uninstall command: the generated uninstaller, or `"C:\Program Files\Remote Lockdown Admin\Uninstall …"`.
5. Detection rule: file exists at the install path, or the uninstall registry key.
6. Assign to a device group; install context **System**.

**Why the `.exe` and not the `.msi` in device context:** an MSI installed as SYSTEM must be a
**per-machine** package. The 1.0.5 MSI is built `perMachine: false` (per-user), which under the SYSTEM
account installs into the SYSTEM profile where no user can see it. The config has been corrected in this
repository, but **until the next Windows build is released, use the NSIS `.exe` for device-context
deployment** — or install the MSI in user context while the user is signed in.

### 2b. Intune — MSI as a Line-of-Business app (once the next build ships)

Line-of-business MSI deployment requires a per-machine package and no UI:

```
msiexec /i remote-lockdown-admin-<version>.msi /qn /norestart
```

Silent (`/qn`) is required: the current MSI has `runAfterFinish: true`, which is fine for a human
double-clicking and wrong for a managed install. Use `/qn` and launch the app from the Start menu.

### 2c. Group Policy / SCCM / plain network share

Copy the installer to a share the machines can read and run it with `\\server\share\…exe /S`, or publish
the MSI through GPO software installation. Files copied over SMB **do not carry the Mark of the Web**, so
no SmartScreen prompt appears. This is also the right route for a lab or a small deployment with no MDM.

### 2d. The agent on managed devices

The agent is **not** shipped as a GitHub download at all: the console hands each device its own installer
(the NSIS wrapper around `lockdown-agent.exe`), generated by the deployment and served from it. That
installer already:

- installs the Windows service `LockdownAgent` as `LocalSystem`, auto-start,
- adds the Defender exclusions (two paths, two processes),
- sets the AC power policy so the machine does not sleep out of reach.

Deploy it the same way — push the installer from the deployment, or run the one-time enrolment command
the console shows. Do **not** distribute the per-device installer from a public URL; it carries that
device's credentials.

## 3. Manual install, when there is no MDM

1. Verify the download against the published checksum before running anything:

```powershell
Get-FileHash .\remote-lockdown-admin-1.0.5.exe -Algorithm SHA256
# compare with SHA256SUMS / SHA256SUMS-<platform> from the same release
Get-AuthenticodeSignature .\remote-lockdown-admin-1.0.5.exe | Format-List Status, SignerCertificate
```

2. Clear the Mark of the Web **after** the checksum matches:

```powershell
Unblock-File .\remote-lockdown-admin-1.0.5.exe
```

3. Run the installer. `Status: NotSigned` in step 1 is expected for current releases (see §4); the
   checksum is what you are actually trusting, which is why step 1 comes first.

## 4. Code signing: what it does and does not buy

Current state: **releases are unsigned.** Consequences, stated without optimism:

| Mechanism | Unsigned today | After signing |
|---|---|---|
| SmartScreen reputation | warns on first run **if downloaded** | still warns on first download — **EV certificates stopped granting instant reputation in 2024**, and Microsoft's docs now say OV and EV "both lead to the same first-download warning" |
| Smart App Control hosts | **blocked outright, no bypass** | runs |
| Defender/EDR heuristics | higher false-positive rate | lower |
| Auto-update integrity | hash-only (`verifyUpdateCodeSignature: false`) | signature-verified |

Signing is therefore **required for Smart App Control and for auto-update integrity**, but it is **not**
a way to skip the first-download warning. The two cheap routes are Azure **Artifact Signing** (formerly
Trusted Signing, ~$9.99/month — check jurisdiction eligibility first: Microsoft lists USA/Canada/EU/UK
organisations, so a Kenyan entity may need another route) or a conventional OV certificate. Details and
the trade-offs are in `docs/CODE_SIGNING.md`.

## 5. Anti-virus and EDR: the risk that outranks SmartScreen

A remote-lockdown agent *behaves* like malware — persistent service, screen lock, input suppression, file
encryption, Defender exclusions. Expect quarantine events. In order:

1. Submit every release build to Microsoft's false-positive portal before a client rollout.
2. Ask the client's security team to allowlist the publisher and the two process names
   (`lockdown-agent.exe`, `lock-screen.exe`) — the installer already excludes them from Defender.
3. Treat **Microsoft Virus Initiative (MVI)** membership as the durable answer for a security product;
   it is a business/partnership track, not a code change, and it should start before the first client.

Do not tell a client to disable their EDR. Offer them the allowlist and the submission evidence instead.

## 6. Packaging requirements a release must meet

Checklist for the Windows build (the automated half is `scripts/win_installer_check.py`):

- [ ] MSI is **per-machine** (required for device-context deployment) — see §2a
- [ ] MSI supports silent install (`/qn`) and silent uninstall
- [ ] NSIS `.exe` accepts `/S` and installs per-machine
- [ ] Installer installs the service as `LocalSystem` with auto-start
- [ ] Uninstall removes the service, the lock-screen binary and the Defender exclusions
- [ ] `SHA256SUMS-windows-x64` published alongside the artefacts
- [ ] Signature state stated in the release notes (signed or unsigned — never silent about it)

## 7. Deploying to a client: order of operations

1. Client creates their own Cloudflare account (§4 of `docs/SERVERLESS-DEPLOY.md`) — one deployment per
   client, no shared tenancy.
2. Set the deployment secrets: `ADMIN_TOKEN`, `JWT_SECRET`, `BACKUP_ENCRYPT_KEY`; a **real, restricted**
   `GOOGLE_API_KEY` or none at all (a placeholder is refused — see `docs/SERVERLESS-DEPLOY.md`).
3. Run setup and create the first admin — the wizard now requires the deployment's setup token.
4. Deploy the console to IT staff via §2a–2c.
5. Enrol devices one at a time from the console; each install adds itself to Defender's exclusions.
6. Confirm the first check-in appears, then run one lock/unlock cycle per device before signing off.

## 8. What to tell the client, in one paragraph

> The console and agent install through your existing management tooling, so no user sees a Windows
> security prompt and nobody clicks through a warning. Builds are currently unsigned; we publish SHA-256
> checksums for every artefact, and signing is scheduled. The agent installs as a system service and
> registers the exclusions it needs with Defender; your security team will also get our false-positive
> submission evidence. Firmware-level protection is not part of this deployment.
