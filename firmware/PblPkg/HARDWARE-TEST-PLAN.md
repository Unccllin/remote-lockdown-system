# PBL Firmware Hardware Test Plan

## Purpose

This document guides you through testing the PBL UEFI firmware on a physical
Windows machine. The firmware has been verified in QEMU+swtpm (10+ test runs);
this plan verifies it works on real hardware.

## Two testing modes

### Mode A: Live test (recommended)

PBL fetches a real verdict from the live serverless Worker at
`https://lockdown-serverless.mainacollins196.workers.dev`. This tests the
full end-to-end flow: firmware → network → Cloudflare Worker → KV → signed
verdict → firmware.

Use the `prepare-live-test.py` script (one command, fully automated):

```bash
cd firmware/PblPkg
pip install cryptography cbor2 requests

# Prepare USB files (downloads firmware + signing key, builds policy, enrolls device)
python3 prepare-live-test.py \
  --server https://lockdown-serverless.mainacollins196.workers.dev \
  --efi-path PblApp.efi \
  --output /tmp/pbl-live-test \
  --device-id "hw-test-001" \
  --status active

# For a LOCKED verdict test:
python3 prepare-live-test.py \
  --server https://lockdown-serverless.mainacollins196.workers.dev \
  --efi-path PblApp.efi \
  --device-id "hw-test-002" \
  --status locked

# For a TRACKING verdict test:
python3 prepare-live-test.py \
  --server https://lockdown-serverless.mainacollins196.workers.dev \
  --efi-path PblApp.efi \
  --device-id "hw-test-003" \
  --status tracking
```

The script outputs a staging directory (`/tmp/pbl-usb-staging/`) containing:
- `EFI/BOOT/BOOTX64.EFI` — the firmware
- `EFI/PBL/policy.cose` — the policy blob (pointing to the live server)

Copy these to a FAT32-formatted USB drive and boot from it.

You can also download the firmware directly from the server:

```bash
curl -o PblApp.efi https://lockdown-serverless.mainacollins196.workers.dev/v1/firmware
```

And fetch the signing key info:

```bash
curl https://lockdown-serverless.mainacollins196.workers.dev/v1/signing-key
```

### Mode B: Mock test (offline)

PBL fetches a verdict from a local mock server (`test-d205.py --serve`).
Use this when you don't have network access or want to test specific
verdict values without server-side state.

See "Step 2" and "Step 3" below for mock server setup.

## What you need

1. A physical Windows PC (x86_64) with UEFI firmware
2. A USB flash drive (FAT32 formatted, at least 32 MB)
3. The built `PblApp.efi` file (from `firmware/PblPkg/PblApp.efi`,
   or downloaded from the live server)
4. A policy blob — either:
   - Generated by `prepare-live-test.py` (live mode), or
   - Generated by `test-d205.py` (mock mode)
5. Network access to the serverless Worker (live mode), or
   a machine running the mock verdict server (mock mode)

## What you can test WITHOUT legitimate Windows

These tests do NOT require a Windows installation or BitLocker:

| Test | Description | Requires Windows? |
|------|-------------|------------------|
| H-1 | Firmware loads during BDS | No |
| H-2 | Policy blob parsing | No |
| H-3 | TPM NV provisioning + HMAC session | No |
| H-4 | Verdict fetch over network | No (needs server) |
| H-5 | X.509 cert chain validation | No |
| H-6 | ES256 signature verification | No |
| H-7 | Lock-state cache (NV write/read) | No |
| H-8 | PCR 12/13 extension | No |
| H-9 | Lock screen display (BLOCK path) | No |
| H-10 | Decision: BLOCK (expected — no BitLocker/DMA) | No |

## What you CANNOT test without legitimate Windows

| Test | Why |
|------|-----|
| PASS path (chain-load Windows) | Requires BitLocker + kernel DMA protection |
| TRACKING verdict (C5) | Requires Windows + agent running |
| BitLocker PCR sealing | Requires BitLocker enrollment |
| Override challenge/response | Requires Windows + agent |

## Step 1: Prepare the USB flash drive

On any machine (Linux, macOS, or Windows):

```bash
# Format the USB drive as FAT32 with GPT partition table
# (Replace /dev/sdX with your USB device — be careful!)

# Linux:
sgdisk --clear --new=1:2048:0 --typecode=1:EF00 /dev/sdX
mkfs.fat -F 32 -n "PBLTEST" /dev/sdX1

# Create directory structure
mkdir -p /mnt/usb/EFI/BOOT
mkdir -p /mnt/usb/EFI/PBL

# Copy firmware and policy
cp PblApp.efi /mnt/usb/EFI/BOOT/BOOTX64.EFI
cp policy.cose /mnt/usb/EFI/PBL/policy.cose

# Unmount
umount /mnt/usb
```

On Windows (PowerShell as Admin):
```powershell
# Format the USB drive as FAT32
Format-Volume -DriveLetter E -FileSystem FAT32 -NewFileSystemLabel "PBLTEST"

# Create directories and copy files
New-Item -ItemType Directory -Force -Path E:\EFI\BOOT
New-Item -ItemType Directory -Force -Path E:\EFI\PBL
Copy-Item PblApp.efi E:\EFI\BOOT\BOOTX64.EFI
Copy-Item policy.cose E:\EFI\PBL\policy.cose
```

## Step 2: Generate the test policy blob

On a machine with Python 3 + cryptography + cbor2:

```bash
cd firmware/PblPkg
pip install cryptography cbor2

# Generate keys (root CA + intermediate CA + leaf cert)
python3 test-d205.py --generate-keys

# Generate policy blob (point to your server IP, not 10.0.2.2)
python3 test-d205.py --generate-policy /tmp/policy.cose \
  --uri "http://<SERVER_IP>:8080/v1/verdict"

# Copy to USB drive
cp /tmp/policy.cose /mnt/usb/EFI/PBL/policy.cose
```

## Step 3: Start the mock verdict server

On a machine reachable from the test hardware:

```bash
cd firmware/PblPkg
python3 test-d205.py --serve --port 8080
```

The server listens on `0.0.0.0:8080` and returns an UNLOCKED verdict.

## Step 4: Boot the test hardware from USB

1. Insert the USB flash drive into the test machine
2. Power on the machine
3. Enter the UEFI/BIOS setup (usually F2, F10, or Del)
4. Configure boot order to boot from USB first
5. **Disable Secure Boot** (PblApp.efi is not yet signed — D-130)
6. Save and exit — the machine should boot from USB

## Step 5: Observe the serial output

PBL outputs diagnostic messages to the serial console. On most machines,
you can capture this via:

### Option A: Serial cable (most reliable)
- Connect a USB-to-serial adapter to the motherboard's serial header
- Capture at 115200 baud, 8N1

### Option B: UEFI serial console redirection
- In UEFI setup, enable "Serial Console Redirection" or "Console Redirection"
- Set COM1 to 115200 baud, 8N1

### Option C: On-screen text (least reliable)
- PBL prints to the console output, which may appear on the screen
- This depends on the UEFI firmware's console support

## Step 6: Verify expected output

The serial output should show:

```
PBL — Pre-Boot Lock v0
[2/8] Parsing policy blob...
  [INFO] policy.cose: <size> bytes
[3/8] Reading TPM NV state...
  [OK] NV indices provisioned
  [OK] HMAC session established (AES-256-CFB)
  [WARN] NV_Read(LOCK_STATE) RC=0x14A   ← first boot, expected
  [INFO] No cached lock state: Not Found
  [WARN] NV_Read(POLICY_VERSION) RC=0x14A ← first boot, expected
  [INFO] No policy version counter: Not Found
  [OK] New policy version 1 (was 0) — incrementing NV counter
  [INFO] POSTing verdict request to http://<SERVER_IP>:8080/v1/verdict
  [OK] Verdict response: 205 bytes
  [OK] Cert chain validated
  [OK] Verdict signature verified (ES256)
  [OK] Verdict decoded: verdict=0 policy_version=1
  [OK] Verdict verified
  [OK] Lock state cached to TPM NV
[7/8] Extending PCR 12/13...
  [OK] PCR HMAC session established
  [OK] PCR 13 (inputs) extended
  [OK] PCR 12 (decision) extended
[8/8] Decision: BLOCK — lock screen
```

### Why BLOCK is expected

The verdict is UNLOCKED (verdict=0), but the decision is BLOCK because:
- BitLocker is not enabled (or not detected)
- Kernel DMA protection is not enabled

This is **correct fail-closed behavior**. The firmware does not allow
boot to Windows unless all platform security checks pass.

## Step 7: Second boot (verify NV persistence)

1. Reboot the machine (Ctrl+Alt+Del or power cycle)
2. Boot from USB again
3. The output should now show:

```
  [OK] NV indices provisioned
  [OK] HMAC session established (AES-256-CFB)
  [OK] NV_Read(LOCK_STATE) — cached verdict found
  [INFO] Cached verdict: 0 (grace_until=...)
  [OK] New policy version 1 (was 1) — already current
```

The second boot should read the cached verdict from TPM NV instead of
fetching from the server (if the server is unreachable, it falls back
to the cache).

## Step 8: Capture the artifact

Save the serial output to a file. This is your hardware test artifact:

```bash
# If using serial cable:
cat /dev/ttyUSB0 > pbl-hardware-test-$(date +%Y%m%d).log

# Name the file with the date and hardware model
mv pbl-hardware-test-*.log firmware/PblPkg/test-output-hardware-<model>-$(date +%Y%m%d).log
```

## Troubleshooting

### Firmware doesn't load
- Verify the USB is bootable (try another machine)
- Verify BOOTX64.EFI is at `EFI/BOOT/BOOTX64.EFI`
- Disable Secure Boot (unsigned firmware)
- Try a different USB port

### No serial output
- Check serial console redirection is enabled in UEFI setup
- Try a different baud rate (9600, 38400)
- Some machines only output to serial after UEFI hands off

### TPM errors
- Ensure TPM is enabled in UEFI setup
- Try clearing TPM (usually an option in UEFI setup)
- Some OEMs disable TPM 2.0 by default

### Network errors
- Verify the server is reachable from the test machine
- Check firewall rules (port 8080)
- Try `http://` not `https://` (firmware doesn't have TLS configured)

### Verdict fetch fails
- Check the `--uri` in the policy blob points to the right IP
- The server must be on a network reachable from the test machine
- Check the server is running (`python3 test-d205.py --serve`)
